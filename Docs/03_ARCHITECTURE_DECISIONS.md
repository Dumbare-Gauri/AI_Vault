# 03 — Architecture Decision Log

Status: **Append-only log.** Every significant technical decision gets an entry here, in order, and entries are never edited to erase history — a reversed decision gets a new ADR that supersedes the old one. See [`00_ENGINEERING_HANDBOOK.md`](00_ENGINEERING_HANDBOOK.md) §30 for when an ADR is required.

Format per entry: Status, Context, Decision, Consequences, Alternatives considered.

---

## ADR-001: Monorepo with pnpm workspaces + Turborepo

**Status:** Accepted

**Context:** `apps/frontend`, `apps/backend`, and `apps/worker` will share types, auth helpers, and the AI Gateway constantly (Handbook §6.1.1, §8.14). Multiple repos would mean either a published internal package registry before Phase 1 starts, or duplicated code drifting out of sync.

**Decision:** Single repository. pnpm workspaces for dependency linking across `apps/*` and `packages/*`; Turborepo for task orchestration/caching (build, lint, test) across the workspace.

**Consequences:** Shared code changes atomically with its consumers in one PR. Repo grows larger over time; CI must scope tasks per-package (Turborepo's affected-package detection) rather than always running everything. Revisit if `apps/*` ever need independent release cadence or separate ownership strong enough to justify a split.

**Alternatives considered:** Polyrepo with a published `@vault/*` npm scope (rejected: package registry + versioning overhead not justified before there's a second consumer team); Nx (comparable to Turborepo; Turborepo chosen for lighter configuration surface at this project's size).

## ADR-002: TypeScript on Node.js (LTS) as the sole language/runtime

**Status:** Superseded in part by [ADR-012](#adr-012-revise-phase-1-stack-vite--react-frontend-fastapi--celery-backendworker) — the platform is polyglot from Phase 1 onward (TypeScript for `apps/frontend`, Python for `apps/backend`/`apps/worker`). Kept for historical context; do not use this ADR to justify a TS-only expectation anywhere in the codebase.

**Context:** `packages/types` needs to be consumed without translation by every app. A single language across frontend, backend, and worker means one shared type system, one hiring/skill profile, one toolchain.

**Decision:** TypeScript everywhere, running on the current Node.js LTS release.

**Consequences:** No polyglot flexibility (e.g. no reaching for Python for AI/data-science-style code without a boundary/FFI decision later). Strict `tsconfig` (via `packages/config`) enforced across all apps/packages from Phase 1.

**Alternatives considered:** Python backend + TS frontend (rejected: would require a serialized contract layer instead of shared `packages/types`, reintroducing the drift problem ADR-001 avoids).

## ADR-003: Next.js for the frontend

**Status:** Superseded by [ADR-012](#adr-012-revise-phase-1-stack-vite--react-frontend-fastapi--celery-backendworker) — the frontend is Vite + React (SPA), not Next.js.

**Context:** `apps/frontend` (Phase 6, Founder Dashboard) needs server-rendered pages for fast initial load of inventory/recommendation views plus API routes for lightweight BFF needs.

**Decision:** Next.js (React) as the frontend framework.

**Consequences:** Couples the frontend to React's ecosystem and Next's conventions (file-based routing, server components). Well-trodden path for the dashboard-style UI described in Handbook's UI/UX standards.

**Alternatives considered:** Plain Vite + React SPA (rejected: would need a separate solution for SSR/SEO-adjacent concerns the dashboard doesn't strictly need yet, but Next costs little extra at this stage and keeps the option open).

## ADR-004: NestJS for the backend API

**Status:** Superseded by [ADR-012](#adr-012-revise-phase-1-stack-vite--react-frontend-fastapi--celery-backendworker) — the backend is FastAPI (Python), not NestJS.

**Context:** `apps/backend` needs enforced layering (Handbook §6.1.2: presentation/application/domain/infrastructure), dependency injection for swappable infrastructure (datastore, AI Gateway, queue producer), and RBAC/guard support from Phase 2 onward.

**Decision:** NestJS as the backend framework.

**Consequences:** Opinionated module/DI structure maps directly onto the layered architecture instead of fighting it. Steeper initial boilerplate than a minimal Express app, accepted as the cost of enforced structure across many future phases and contributors.

**Alternatives considered:** Express + hand-rolled layering (rejected: layering would be convention-only with nothing stopping drift over 8 phases); Fastify (comparable performance profile, less mature DI/module story for this project's layering needs).

## ADR-005: Node.js worker on BullMQ, Redis as queue/cache

**Status:** Accepted for the Redis choice; the queue *library* is superseded by [ADR-012](#adr-012-revise-phase-1-stack-vite--react-frontend-fastapi--celery-backendworker) — the worker is Python (Celery), so BullMQ (a Node.js library) does not apply. Redis remains the broker/cache exactly as decided here.

**Context:** Handbook §8.15 requires the worker to be a stateless, horizontally scalable queue consumer with durable job state and retry semantics — needed as soon as Phase 3's scanner has to walk large storage accounts without blocking a request.

**Decision:** BullMQ (Redis-backed) as the job queue; Redis doubles as the cache layer for hot read paths.

**Consequences:** Redis becomes a required piece of local/dev infrastructure from Phase 1's `infrastructure/docker` setup onward. BullMQ's retry/backoff/dead-letter primitives are used directly rather than hand-rolled, keeping worker job-handling logic thin.

**Alternatives considered:** SQS/cloud-managed queue (rejected for local-dev friction pre-deployment-target decision); a Postgres-backed job queue (rejected: would couple job throughput to the primary datastore's write load).

## ADR-006: PostgreSQL as the primary datastore

**Status:** Accepted

**Context:** Inventory data (Handbook §8.2), recommendations (§8.6), RBAC/audit data (§13), and relational structures (files ↔ folders ↔ permissions ↔ tenants) all benefit from strong relational integrity and transactional guarantees, plus mature JSON column support for connector-specific metadata that doesn't need its own table.

**Decision:** PostgreSQL as the single primary datastore across phases.

**Consequences:** One datastore to operate, back up, and reason about for consistency. `tenant_id`-scoped schema/row-level patterns (Handbook §13) are enforced via Postgres constraints/RLS where practical, not just application code. A dedicated search/vector store is a separate future ADR if Phase 4/5's similarity search needs outgrow Postgres extensions (e.g. `pgvector`).

**Alternatives considered:** MongoDB (rejected: weaker fit for the relational audit/RBAC/tenant model this system leans on throughout); separate OLTP + document store from day one (rejected as premature — revisit only if a concrete phase requirement demands it).

## ADR-007: AI Gateway as an internal provider-agnostic abstraction

**Status:** Accepted

**Context:** Handbook §12 — the LLM must be replaceable without touching `apps/*` business logic. This has to be a real architectural boundary, not a naming convention.

**Decision:** A single module in `packages/shared` (the AI Gateway) is the only code in the repository permitted to import a provider SDK. It exposes capability-based methods (`complete`, `embed`, `classify`, …) with provider selection as an internal routing decision. Each supported provider (Claude, GPT, Gemini, Ollama, Qwen, Mistral) gets a thin adapter behind that interface, implemented as each phase actually needs it — not all six on day one.

**Consequences:** Every call site depends on the Gateway's interface, never a provider type. Adding/removing/swapping a provider touches only the Gateway + its adapter. This is enforced by code review (Handbook §26 review checklist) and can be enforced mechanically later (e.g. a lint rule banning provider-SDK imports outside `packages/shared`) once the tooling exists.

**Alternatives considered:** Direct provider SDK calls per app with a shared "prompt library" (rejected — this is exactly the coupling the AI Philosophy in Handbook §12 exists to prevent); a third-party LLM router service (rejected for now — adds an external dependency/cost before there's a concrete multi-provider requirement; revisit if adapter maintenance burden grows).

## ADR-008: Git branching — main / production / develop / feature

**Status:** Accepted

**Context:** Need a branching model that supports the sprint lifecycle in Handbook §4 (phase implemented → manually tested → CTO-reviewed → released) with a clear, always-deployable integration point and an explicit production gate.

**Decision:** Four-tier model as documented in Handbook §24-25: `feature/*` → `develop` (PR + CI + review) → `production` (promoted after manual test + CTO review) → `main` (tagged releases only). No direct pushes to the three long-lived branches.

**Consequences:** Every change is traceable through a PR. An extra promotion step (`develop` → `production` → `main`) versus a simpler two-branch model, accepted because the lifecycle already requires a manual-test gate and a CTO-review gate as distinct steps — the branch structure just makes those gates visible in git history instead of implicit.

**Alternatives considered:** Trunk-based development with feature flags (rejected: the sprint lifecycle's explicit human gates fit a promotion-branch model more directly than flag-gated trunk); GitHub Flow (`main` + `feature/*` only) (rejected: collapses the manual-test and production-release gates into one branch, losing the distinction).

## ADR-009: Docker Compose for local/dev infra, GitHub Actions for CI/CD

**Status:** Accepted

**Context:** Phase 1 needs a reproducible local environment (Postgres, Redis, the three apps) and a CI pipeline that can run lint/typecheck/test on every PR per the Git strategy's merge policy (Handbook §24).

**Decision:** Docker + Docker Compose for local development infra (`infrastructure/docker`). GitHub Actions for CI/CD (`.github/workflows`), since the repo is already GitHub-hosted and Actions needs no separate CI system to operate.

**Consequences:** Deployment target (the orchestrator production actually runs on — Kubernetes, ECS, a PaaS, etc.) remains an open decision, deliberately deferred to a later ADR once Phase 1/8 requirements make the tradeoffs concrete rather than guessed at now.

**Alternatives considered:** None seriously considered for local dev (Compose is the standard fit for a multi-service TS monorepo); CircleCI/Jenkins for CI (rejected: adds an external system with no advantage over Actions given GitHub hosting).

## ADR-010: Caveman Repository workflow as standard operating discipline

**Status:** Accepted

**Context:** Handbook §29. As the repo grows across 8 phases, "load the whole repo into context for every task" stops scaling — for a human skimming files or an AI agent implementing a phase.

**Decision:** Standardize on loading only the modules a task's phase document identifies as affected, using this handbook + the relevant phase doc + targeted search as the primary navigation aids, documented as a workflow discipline rather than tied to any specific tool.

**Consequences:** Makes the strict module boundaries in Handbook §5-6.1 load-bearing, not just tidy — they're what makes "only the affected modules" a well-defined, small set in the first place. Tool-agnostic, so it survives a change of IDE/agent/editor.

**Alternatives considered:** Full-repository context loading per task (rejected — doesn't scale past a couple of phases, and makes diffs harder to keep scoped per the PR review checklist).

## ADR-011: Expand platform architecture from storage cleanup to a full knowledge-brain pipeline

**Status:** Accepted

**Context:** The original Engineering Handbook scoped System Architecture around ten subsections (§5.1-5.10 in the pre-revision numbering) sufficient to describe scan → recommend → execute for storage hygiene. The product vision (Handbook §1, Project Master §1-2) is broader: an "AI Employee" that understands, organizes, learns, connects, recommends, executes, and protects an organization's knowledge — storage cleanup is the first slice, not the ceiling. The handbook needed to name the additional pipeline stages (Metadata Engine, Knowledge Builder, Embedding Engine, Search Engine, Notification Engine, Audit Engine) and platform-facing modules (Founder Dashboard, Employee Dashboard, Authentication) explicitly, so later phases have module contracts to implement against instead of inventing them ad hoc mid-phase.

**Decision:** Expand the Core Platform Modules section (Handbook §8) to fifteen modules with explicit Purpose/Responsibilities/Inputs/Outputs/Dependencies/Future Expansion contracts; add Database Philosophy (§9), AI Intelligence Pipeline (§10), Founder/Employee Journeys (§14-15), Department Intelligence (§16), a Recommendation Engine deep dive (§17), and Future Connector Architecture (§18) as dedicated sections. No existing architectural decision (technology stack, AI Gateway abstraction, layering, event-driven processing, Git strategy) was changed — this is additive scope on top of ADR-001 through ADR-010, not a replacement of any of them. All existing handbook section numbers shifted to accommodate the new material; every cross-reference to a handbook section elsewhere in `Docs/` was updated in the same pass.

**Consequences:** Phases 3-7 now have named modules to implement against (e.g. Phase 4 "Storage Intelligence" maps onto the Metadata Engine + Knowledge Builder contracts, §8.3-8.4) rather than being scoped from a vaguer "storage intelligence" description. Department Intelligence (§16) is explicitly profile-based, not per-department AI agents — a constraint future phases must not violate without a new ADR. Section-number churn is a one-time cost, absorbed in this revision; future handbook edits should prefer appending subsections over renumbering where practical, to avoid repeating this cross-reference maintenance.

**Alternatives considered:** Leaving the new modules undocumented until their phase is scoped (rejected — the phase docs for 4-7 already reference the modules by name in their Objective sections, e.g. Phase 4/5's dependency on scanner/recommendation-engine concepts, and Documentation Standards §27 requires a phase's Architecture section to fit the system architecture, which requires the architecture to already describe the module); a separate "Platform Modules" document outside the handbook (rejected — Handbook §2 states it is *the* single source of truth for how the system is built, and splitting module contracts out would fragment that).

## ADR-012: Revise Phase 1 stack — Vite + React frontend, FastAPI + Celery backend/worker

**Status:** Accepted

**Context:** [`PHASE_01_FOUNDATION.md`](phases/PHASE_01_FOUNDATION.md) (CTO-authored, founder-approved) specifies a different implementation stack than ADR-002/003/004/005 had converged on: React 19 + Vite (not Next.js) for `apps/frontend`; FastAPI + SQLAlchemy 2 + Alembic + Pydantic v2 (not NestJS) for `apps/backend`; Celery (not BullMQ) for `apps/worker`. The founder confirmed, when asked directly at the start of Phase 1 implementation, that the Phase 1 document's stack is authoritative over the Handbook's — the Handbook was stale on this point, not the phase doc. Per Handbook §30, an ADR must record this before the code lands, not after.

**Decision:** Adopt a **polyglot monorepo**: TypeScript for `apps/frontend` and the frontend-facing packages (`packages/types`, `packages/ui`, the TS half of `packages/config`); Python (3.13, current stable) for `apps/backend` and `apps/worker`, sharing a Python package under `packages/shared` for cross-cutting concerns (structured logging, typed errors, config loading) instead of a TS one. Concretely:
- Frontend: Vite + React 19 + TypeScript + Tailwind CSS v4 + TanStack Router/Query + Zustand + React Hook Form + Zod + shadcn/ui. Next.js (ADR-003) is dropped — no SSR requirement has materialized and a SPA is simpler to operate for a dashboard-style app.
- Backend: FastAPI + SQLAlchemy 2 + Alembic + Pydantic v2, still organized into the Handbook §6.1.2 presentation/application/domain/infrastructure layers — that layering is framework-agnostic and holds under FastAPI exactly as it would under NestJS. NestJS (ADR-004) is dropped.
- Worker: Celery, still consuming Redis (ADR-005's Redis decision is retained in full — only the Node.js BullMQ library is dropped in favor of Celery, Python's equivalent).
- pnpm workspaces + Turborepo (ADR-001) are retained, but scoped to the TypeScript portion of the tree (`apps/frontend` + TS `packages/*`) since Python has no place in a pnpm workspace. The Python apps (`apps/backend`, `apps/worker`, `packages/shared`) are each independent Python projects (`pyproject.toml`), with `packages/shared` installed into the other two as an editable local dependency.

**Consequences:** `packages/types`'s original promise — "one shared type system, zero translation layer" (ADR-002) — no longer holds across the whole stack: Python (Pydantic) and TypeScript can't share a type definition directly. API contracts must be kept in sync manually in Phase 1, with FastAPI's auto-generated OpenAPI schema as the source of truth; generating TS types from that OpenAPI schema (e.g. `openapi-typescript`) is flagged as follow-up tooling work for an early future phase, not solved now. `packages/shared` is no longer TypeScript — anything under it must be Python, and any future TS cross-cutting code shared only among frontend-adjacent TS packages belongs in `packages/config` or a new TS-specific package, not here. CI (§11, §21) now needs two independent toolchains (Node + Python) rather than one, which is reflected in `.github/workflows/ci.yml`'s job matrix.

**Alternatives considered:** Keep the original TS-everywhere stack and treat the Phase 1 document as the one that's wrong (rejected — the founder explicitly confirmed the Phase 1 document is authoritative for this decision when the conflict was surfaced); rewrite `packages/types` as a codegen target from day one (deferred, not rejected outright — reasonable future work once the backend's OpenAPI surface is non-trivial, but premature for a Phase 1 that has no business endpoints yet).

## ADR-013: Phase 2 session strategy — client-side Google Identity Services, short-lived JWT + rotating httpOnly refresh cookie

**Status:** Accepted

**Context:** [`PHASE_02_AUTH.md`](phases/PHASE_02_AUTH.md) specifies Google OAuth 2.0 login, JWT access tokens, and a refresh token flow, but leaves the concrete mechanics as an implementation decision ("Claude may choose... as long as they follow the Engineering Handbook"). Two materially different architectures were viable: (1) a server-side Authorization Code redirect flow (backend redirects to Google, Google redirects back to a backend callback with a `code`, backend exchanges it for tokens using `GOOGLE_CLIENT_SECRET`), or (2) a client-side Google Identity Services (GSI) flow (frontend renders a "Sign in with Google" button, receives a signed ID token directly from Google, POSTs it to the backend for verification). The phase document's API scope literally lists `POST /auth/login` — a shape that fits the client-side flow (a single fetch call with a credential in the body) much more naturally than a redirect-initiating endpoint, which is conventionally `GET`. `GOOGLE_CLIENT_SECRET` was already provisioned as a placeholder in Phase 1's `.env.example`, which pointed toward the server-side flow instead. Asked directly, the founder chose the client-side GSI flow.

**Decision:**
- **Sign-in mechanics:** Frontend loads Google's GSI script (`https://accounts.google.com/gsi/client`, a static tag in `index.html`, not an npm package), renders the standard "Sign in with Google" button (`GoogleSignInButton`, `apps/frontend/src/components/google-sign-in-button.tsx`), and receives a signed ID token as the button's callback argument. The frontend POSTs `{ id_token }` to `POST /v1/auth/login`. The backend verifies the token's signature and claims against Google's public keys via the `google-auth` library (`GoogleIdentityVerifier`, `apps/backend/app/infrastructure/auth/google_identity.py`) — never trusting unverified claims. No redirect, no server-side callback route, no CSRF-state cookie dance — GSI's signed credential is the whole security boundary for this step. `GOOGLE_CLIENT_SECRET` remains an unused-until-Phase-3 placeholder: Phase 3's Workspace Connector needs a genuinely different, separate OAuth interaction (server-side, Drive-scoped, offline access) that this decision does not preempt or design against yet.
- **Session tokens:** On successful verification (and find-or-create of the Organization/User/Role), the backend issues two tokens: a short-lived JWT **access token** (15 min default, HS256, claims: `sub`/`org`/`role`, Handbook §13 RBAC context attached to every authenticated request) returned in the response body and kept only in frontend memory (a module-level variable in `apps/frontend/src/lib/session.ts`, never `localStorage`, never a cookie — immune to a cookie-focused CSRF attack and cleared on tab close); and an opaque, high-entropy **refresh token** (30 days default) set as an `httpOnly`, `Secure`-when-not-local, `SameSite=Lax` cookie scoped to `path=/v1/auth` (least-privilege: the browser only attaches it to the auth endpoints, not every API call). Only the refresh token's SHA-256 hash is ever persisted (`refresh_tokens.token_hash`) — Handbook §13's "encrypt sensitive tokens before persistence."
- **Rotation and reuse detection:** Every `POST /v1/auth/refresh` call revokes the presented refresh token and issues a new one (rotation). Presenting an already-revoked token is treated as a theft signal: the entire token family for that user is revoked immediately (`RefreshTokenRepository.revoke_all_for_user`) and the attempt is written to `audit_logs` as `refresh_token_reuse_detected`, rather than just rejecting the one request.
- **Session recovery / silent refresh:** `apps/frontend/src/lib/session.ts` is a neutral module (no store or api-client import either direction) holding the current access token and a refresh-handler callback the auth store (`apps/frontend/src/stores/auth-store.ts`, Zustand) registers at load time. `api-client.ts`'s fetch wrapper attaches `Authorization: Bearer <token>` from this module and, on a 401 from any endpoint *other than* `/v1/auth/*` itself, calls the registered handler once and retries the original request with the refreshed token before giving up — this is what makes an expired access token invisible to the rest of the app. The same handler is called once at app boot (`main.tsx`, before the router's route guards run) to recover a session from a still-valid refresh cookie after a page reload.
- **Rate limiting:** `POST /v1/auth/login` and `/refresh` are rate-limited per client IP via a Redis fixed-window counter (`app/presentation/dependencies/rate_limit.py`) that fails open on a Redis outage — deliberately, since rate limiting here is defense-in-depth, not the primary control (token/signature validation is), and a Redis blip must never be the reason sign-in goes down.

**Consequences:** No CSRF-state cookie or server-side OAuth callback route exists in this codebase for user sign-in — a future contributor must not assume one when reading Phase 3's Workspace Connector spec, which needs its *own*, separate server-side OAuth flow for Drive scopes. The access token is unusable after a tab closes or a hard refresh without a valid refresh cookie, by design (session recovery re-authenticates via the cookie, never by resurrecting a token from storage). `packages/types`'s `AuthSession`/`UserProfile`/`Organization` (`packages/types/src/auth.ts`) are hand-kept in sync with `apps/backend/app/presentation/api/v1/schemas.py`, same manual-sync caveat as ADR-012.

**Alternatives considered:** Server-side Authorization Code redirect flow (rejected per the founder's explicit choice — see Context); storing the access token in `localStorage` for simplicity (rejected — Handbook §13 security-first principle, and it reopens the exact XSS-token-theft class the memory-only + httpOnly-cookie split is designed to close); a single long-lived token with no rotation (rejected — Handbook §13's "every execution must be logged" / audit-first posture expects a detectable signal on token theft, which only rotation + reuse detection provides).

## ADR-014: Phase 3 Google Workspace Connector — server-side Authorization Code flow with a frontend-hosted callback, encrypted token storage

**Status:** Accepted

**Context:** Phase 3 needs the exact flow ADR-013 deliberately deferred: a durable, refreshable, offline-capable connection to a Google Workspace account for future Drive access (Phase 4's scanner), not a per-user identity check. [`PHASE_03_STORAGE_SCANNER.md`](phases/PHASE_03_STORAGE_SCANNER.md)'s API scope lists `POST /connectors/google/connect` and `POST /connectors/google/callback` — both POST, which is unusual for an OAuth-initiating/callback pair (a browser redirect to Google is inherently a `GET` navigation, and Google's redirect back is also a `GET`). Read literally alongside "Google Workspace Integration: OAuth authorization flow, secure callback handling... token persistence, automatic refresh," the design this implies is: the backend never hosts a callback endpoint Google redirects to directly; instead, Google's `redirect_uri` points at a **frontend** route, which extracts `code`/`state` from its own URL and then POSTs them to the backend — hence "POST callback."

**Decision:**
- **Initiate:** `POST /v1/connectors/google/connect` (owner/admin only) generates a single-use, Redis-backed OAuth `state` value (`app/infrastructure/connectors/oauth_state.py`, TTL 10 min, keyed to the requesting organization+user, deleted on first read — Handbook §13's "prevent replay attacks during OAuth" and "validate state parameters") and returns `{ authorize_url }` as JSON. The frontend does a real top-level navigation (`window.location.href = authorize_url`), not a fetch — this must be a full page navigation for Google's own redirect back to work.
- **Callback:** Google redirects the browser (a `GET`, Google's mechanism, not ours) to `GOOGLE_WORKSPACE_REDIRECT_URI` — a **frontend** route, `apps/frontend/src/routes/connectors.google.callback.tsx`. That page reads `code`/`state` off its own URL and POSTs them to `POST /v1/connectors/google/callback` (owner/admin only), which validates the state (rejecting it if the authenticated caller's organization doesn't match the one the state was issued for — cross-organization replay protection beyond the TTL/single-use guarantee alone), exchanges the code for tokens using `GOOGLE_CLIENT_SECRET` (server-to-server, via `requests`, never exposed to the browser), and fetches account info (email + `hd` claim as the workspace domain) from Google's OIDC userinfo endpoint. No backend-hosted redirect target exists anywhere in this flow.
- **Scopes and offline access:** Requests `openid email profile https://www.googleapis.com/auth/drive.readonly` with `access_type=offline&prompt=consent` — Drive scope is requested now (even though Phase 3 does no scanning) specifically so Phase 4 doesn't need a second consent round-trip; `prompt=consent` forces Google to reissue a refresh token even on a re-connect. A callback that doesn't receive a refresh token is treated as a hard failure with instructions to revoke-and-retry, not silently accepted.
- **Storage:** One `storage_connectors` row per (organization, provider) — reconnecting updates the same row, which is also what makes "reject a duplicate connect attempt while already connected" a simple status check rather than needing separate de-duplication logic. Tokens live in a separate one-to-one `connector_credentials` table, encrypted with Fernet (`app/infrastructure/security/encryption.py`, `CONNECTOR_ENCRYPTION_KEY`) — symmetric, reversible encryption, not the one-way hashing ADR-013 used for refresh-session tokens, because these tokens must be *used* (sent to Google), not merely compared. The credentials row is deleted (not blanked) on disconnect; Google's revoke endpoint is called best-effort first.
- **Automatic refresh:** `ConnectorService.get_valid_access_token()` is the only way any code (this phase's `/verify` endpoint today, Phase 4's scanner tomorrow) obtains a usable access token — it transparently refreshes via the stored refresh token if the current one is expired or expiring within 60 seconds, persists the new token, and returns it. Callers never touch `connector_credentials` or the OAuth client directly, which is what makes "prevent invalid tokens from reaching later phases" (the phase spec's own words) structurally true rather than a convention to remember.
- **No `UserRole`-style DB simplification here** — unlike ADR-013's role join table, Phase 3's `Provider Configuration` and `Synchronization Metadata` entities (both listed as placeholder/deferred in the phase spec) are represented as, respectively, code-level `Settings` fields (single global OAuth app registration — no per-tenant BYO-OAuth-app support yet) and a single nullable `last_synced_at` column on `storage_connectors`, rather than dedicated tables with no real rows to put in them yet.

**Consequences:** The backend has no route that Google can redirect to directly for *this* flow — a future contributor extending the connector platform (e.g. adding OneDrive) must follow the same frontend-hosted-callback shape, not assume a backend GET callback exists anywhere in this codebase. `CONNECTOR_ENCRYPTION_KEY` is a new required secret with no safe default (unlike `JWT_SECRET`, which at least has a working-but-insecure placeholder) — `encrypt_token`/`decrypt_token` raise immediately if it's unset, by design, rather than silently using a well-known key. Phase 4's scanner depends on `ConnectorService.get_valid_access_token()` existing and already being correct; it should not reimplement token refresh.

**Alternatives considered:** A backend-hosted `GET /connectors/google/callback` receiving Google's redirect directly (rejected — contradicts the phase spec's literal `POST` verb, and would require the backend to either render an HTML page or issue its own redirect back to the frontend anyway, adding a hop for no benefit given the frontend already needs a route to show connection progress); storing OAuth state in a signed cookie instead of Redis (rejected — Redis is already a hard dependency, Handbook §8.15, and a server-side store lets us bind the state to the requesting organization/user without trusting anything the client presents); hashing tokens like ADR-013's refresh tokens instead of encrypting them (rejected — these tokens must be recoverable in plaintext to call Google's APIs, which a one-way hash structurally cannot support).

## ADR-015: Extract DB/security/connector code from `apps/backend` into `packages/shared` ahead of Phase 4

**Status:** Accepted

**Context:** [`PHASE_04_STORAGE_INTELLIGENCE.md`](phases/PHASE_04_STORAGE_INTELLIGENCE.md) requires the Storage Scanner to run as a worker job (Handbook §8.15: "the worker hosts all async pipeline stages"), reading and writing `StorageConnector`/`ConnectorCredentials` and the new `StorageSource`/`Folder`/`File` inventory tables. Through Phase 3, every SQLAlchemy model, repository, the DB session/engine, token encryption, and the Google Workspace OAuth client lived under `apps/backend/app/infrastructure/` — invisible to `apps/worker`, which had its own separate venv and had never imported backend code (nor should it: `apps/backend` and `apps/worker` are independently deployable Python projects, ADR-012). Phase 4 cannot proceed without a home for this code that both apps can import identically.

**Decision:** Move every DB model, repository, the `Base`/engine/session-factory module, `encrypt_token`/`decrypt_token`, and the `GoogleWorkspaceOAuthClient` from `apps/backend/app/infrastructure/*` into `packages/shared/vault_shared/*` (mirroring the existing sub-package layout: `db/models`, `db/repositories`, `db/session`, `security/encryption`, `connectors/google_workspace`). `apps/backend` and `apps/worker` each keep installing `packages/shared` as an editable local dependency (unchanged from ADR-012), so this is a pure relocation, not a new dependency mechanism.

`ConnectorService` (Phase 3, `apps/backend/app/application/connector_service.py`) does not move wholesale — it was split. Its `initiate_connect`/`complete_connect` methods depend on `apps/backend/app/infrastructure/connectors/oauth_state.py`'s Redis-backed CSRF state, which exists solely to protect the backend's interactive HTTP OAuth flow and has no meaning to a worker job. Moving the whole class would have forced either `packages/shared` to depend on that backend-only presentation-layer concern, or `oauth_state.py` to move too (wrong — the worker never initiates an OAuth handshake). Instead, only the token-refresh piece — `get_valid_access_token()` — was extracted into a new `ConnectorTokenService` (`packages/shared/vault_shared/connector_service.py`). The backend's `ConnectorService` now composes `ConnectorTokenService` for that piece and keeps `initiate_connect`/`complete_connect` (and `oauth_state.py`) exactly where they were.

**Consequences:** `apps/worker` can now import `vault_shared.db.session`, `vault_shared.db.models`, `vault_shared.db.repositories`, and — critically — `vault_shared.connector_service.ConnectorTokenService`, which is the *only* way Phase 4's scanner obtains a usable Google access token; it never touches `ConnectorCredentials` or `GoogleWorkspaceOAuthClient` directly, same guarantee ADR-014 established for the backend. All 96 backend and 18 worker unit/integration tests from Phases 1-3 pass unchanged after the move (import paths updated, no behavior changed). A future contributor adding a new cross-cutting DB model or provider client should default to `packages/shared`, not `apps/backend/app/infrastructure`, unless the code is genuinely presentation-layer/HTTP-flow-specific like `oauth_state.py`.

Separately, and unrelated to the code move itself: mypy could not resolve `vault_shared` when run as a bare `mypy` in either app without the repo's actual CI invocation (`mypy --config-file ../../packages/config/python/mypy.ini app` / `worker`) — the shared `mypy.ini` already sets `ignore_missing_imports = True`, which was already covering this. No config change was needed; this is noted here only because it cost time to rule out during Phase 4 and future contributors should always validate mypy the same way CI does (with `--config-file`), not with bare `mypy`.

**Alternatives considered:** Publish `packages/shared` as its own installable artifact with versioning (rejected — no second consumer team or independent release cadence exists yet, same reasoning ADR-001 used against a polyrepo split); give `apps/worker` a second editable install of `apps/backend` itself (rejected — backend has FastAPI/uvicorn/auth-presentation dependencies the worker has no business installing, and it would violate the independent-deployability boundary ADR-012 relies on); move `ConnectorService` wholesale and have the worker construct a no-op/fake `oauth_state` (rejected — papering over a real layering violation with a stub is worse than the extra split, and would let a future phase's worker code accidentally call `initiate_connect`/`complete_connect`, which make no sense outside an HTTP request).

## ADR-016: Storage Scanner design — two-pass hierarchy resolution, cooperative cancellation, job-level retry

**Status:** Accepted

**Context:** [`PHASE_04_STORAGE_INTELLIGENCE.md`](phases/PHASE_04_STORAGE_INTELLIGENCE.md) requires a provider-agnostic, read-only scanner that traverses every drive a connector exposes, normalizes metadata into `Folder`/`File` rows with materialized paths, runs through the worker queue, and supports resumability, fault tolerance, and cancellation — but leaves the concrete traversal/persistence algorithm as an implementation decision. Three shapes of problem needed a resolved design before writing `ScannerService`: (1) Google Drive's `files.list` API gives no ordering guarantee — a folder can be paginated *after* its own children — which conflicts with wanting to stream-persist items one page at a time rather than loading a whole drive into memory; (2) transient Google API failures (rate limits, network blips) must not fail an entire scan outright; (3) a user must be able to cancel a long-running scan without killing the worker process.

**Decision:**
- **Two-pass ingest per source.** Pass 1 (`_ingest_full`/`_ingest_incremental`) streams pages from Drive's `files.list`/`changes.list` and upserts each `Folder`/`File` immediately with a placeholder path (`/<name>`) and `parent_folder_id = NULL`, committing every 200 items (`_BATCH_COMMIT_SIZE`) to bound memory and cap how much work a crash mid-scan can lose. Pass 2 (`_resolve_hierarchy`) runs once per source after ingest completes: it re-reads only that source's `Folder` rows from our own database (a small subset of all items even at reference scale), builds an in-memory `provider_file_id → Folder` map, and computes each folder's real materialized path via a memoized recursive walk of `provider_parent_id` chains (cycle-guarded — Drive shouldn't produce a parent cycle, but external API data is never trusted blindly). `File` paths are then resolved the same way against the now-correct folder map. This makes ingest order irrelevant to the final path, without ever holding the whole drive in memory at once.
- **Cooperative cancellation.** `ScanJob.cancel_requested` (a boolean column, set by the backend's `POST /v1/scans/{id}/cancel`) is polled once per page fetch and once per source boundary via `ScanJobRepository.is_cancel_requested()` — a column-only query (`session.query(ScanJob.cancel_requested)...`), not an entity fetch, specifically because the worker's long-lived session would otherwise return its own stale identity-mapped `ScanJob` object rather than seeing a cancellation flag set by a *different* process (the backend, in its own session, handling the user's cancel request). A cancelled scan leaves whatever was already committed in place — including any source whose hierarchy-resolution pass hadn't run yet, so that source's placeholder paths persist until the next full scan reconciles them. This is an accepted interim state (the job's `CANCELLED` status is the signal that inventory for that scan is incomplete/stale), not a bug to fix by adding rollback-on-cancel semantics.
- **Job-level retry on transient failures, not page-level.** `ScannerService.run()` lets `DependencyUnavailableError` (Google Drive unreachable, rate-limited, or erroring) propagate out uncaught — deliberately leaving the job `RUNNING`, not `FAILED` — so `apps/worker/worker/tasks/scan.py`'s Celery task (`bind=True`, `max_retries=5`, 30s backoff) can retry the *entire* job. Retrying the whole job rather than resuming mid-source is a deliberate simplification: `ScanProgress` creation is guarded to be idempotent (`get_for_job` before `create_for_job`, since `scan_progress.scan_job_id` is a primary key a retry would otherwise collide on), and every `Folder`/`File`/`StorageSource` write is an upsert, so a full job-level retry safely re-does completed sources rather than corrupting them — just at the cost of re-fetching pages already fetched once. Only once Celery's retries are exhausted does the task itself mark the job `FAILED`. Any other exception (a bug, a data-shape surprise) is caught inside `run()` itself and marks the job `FAILED` immediately — those are not worth retrying blindly.
- **Change-token strategy.** Each `StorageSource.change_token` stores Google's `startPageToken` from `changes.list`. A source scans full (`_ingest_full`) whenever its `change_token` is `NULL` or the requested `scan_type` is `full`; otherwise it scans incremental (`_ingest_incremental`) starting from the stored token, applying `changes.list`'s reported removals/trashes as deletes (`FolderRepository`/`FileRepository.delete_by_source_and_provider_id`, relying on cascading FKs for any descendants) and everything else as upserts, then re-resolving hierarchy only if anything actually changed (`touched`).

**Consequences:** A future contributor extending the scanner to a second provider (Handbook §18) must supply the same two-pass shape (stream-ingest with placeholders, then a bounded resolve pass) if that provider's list API also lacks ordering guarantees — this is not Google-Drive-specific by design, `GoogleDriveClient` is the only place provider detail leaks in. A cancelled or job-retried scan can leave transient wrong-looking placeholder paths on partially-scanned sources until the next successful scan for that source — Phase 5+ code reading `Folder`/`File` rows should treat a `ScanJob` in a non-`COMPLETED` terminal state as a signal that inventory may be stale, not assume every row's `path` is always authoritative. Deep folder trees rely on Python's default recursion limit inside `_resolve_hierarchy`'s memoized walk; this is an accepted limitation for now (typical Drive hierarchies are nowhere near that deep) and not engineered around in this phase.

**Alternatives considered:** A single-pass ingest that defers writing any row until its full ancestor chain is known (rejected — would require buffering an unbounded number of not-yet-placeable items in memory, exactly the scalability problem Phase 4 asks to avoid); per-page or per-item retry with immediate resumption at the failed page (rejected — meaningfully more complex to make crash-safe and idempotent than a job-level retry, for a failure mode — Google API unavailability — that resolves in seconds to low minutes, not worth the complexity given upserts already make a full retry cheap and correct); marking a cancelled scan `FAILED` instead of a distinct `CANCELLED` status (rejected — the phase spec and frontend need to distinguish "the user stopped this on purpose" from "this broke," and `ScanStatus.CANCELLED` already exists as its own state for exactly that reason).

## ADR-017: Knowledge Engine (Phase 5) — deterministic-first pipeline, content extraction, and scan→enrichment chaining

**Status:** Accepted

**Context:** [`PHASE_04_STORAGE_INTELLIGENCE.md`](phases/PHASE_04_STORAGE_INTELLIGENCE.md) is, per its own in-document title, "Metadata Intelligence & Knowledge Engine" (Phase 4's real filename is stale, same class of mismatch as Phase 3's — see the CTO Dashboard's Technical Debt). It asks for a modular enrichment pipeline over the Storage Scanner's inventory (Handbook §8.3 Metadata Engine, §8.4 Knowledge Builder) that is deterministic-first, explicitly must not call the AI Gateway except where "explicitly configured," and must leave the architecture ready for a future Embedding Engine without implementing one now. Several concrete design questions had no single spec answer: how enrichment jobs relate to scan jobs, where file *content* (not just metadata) gets read given Phase 4's scanner was deliberately metadata-only, how deterministic classification/relationship rules should be scoped so they stay explainable rather than an unbounded similarity graph, and how per-file/per-processor failures stay isolated per the phase's explicit error-handling requirement.

**Decision:**
- **Two new worker-owned concerns, one new backend-owned read surface.** `apps/worker/worker/enrichment/` hosts everything that touches file content or runs a processor (`extraction.py`, `processors.py`, `naming.py`, `relationships.py`, `enrichment_service.py`) plus its Celery task (`tasks/enrichment.py`) — mirroring `worker/scanner/`'s shape exactly. `apps/backend` gets only a thin `FileService` (read-only assembly of what the worker already wrote) and `EnrichmentJobService` (start/list/get/cancel, mirroring `ScanService`) — it never runs a processor or touches Drive content itself.
- **Content extraction is real, bounded, in-memory-only reading of file bytes.** Unlike Phase 4's metadata-only scanner, the Knowledge Engine genuinely needs text content (PDF/DOCX/XLSX/PPTX/TXT/Markdown, plus Google-native Docs/Sheets/Slides via Drive's `export` endpoint rather than `download`, since native files have no raw bytes). `GoogleDriveClient` gained `download_file`/`export_file` for this — still strictly read-only against Drive, same `drive.readonly` scope already granted since Phase 3 (no new consent needed). A 20MB size cap skips extraction outright for larger files, and extracted text is sanitized (control characters stripped) and truncated to 200,000 characters before storage — bounded by design, not by observed problems, since nothing in this pipeline should hold an unbounded amount of one file's content in memory or in a row.
- **Ten single-file processors plus a bounded, three-type cross-file relationship pass**, exactly mapping to the phase spec's "suggested processors" list (Extension Normalizer, MIME Validator, File Type Classifier, Folder Context Analyzer, Naming Pattern Analyzer, Ownership Analyzer, Sharing Analyzer, Language Detection as single-file `FileProcessor`s; Version Detection and Duplicate Candidate Detector as the cross-file `RelationshipDiscoveryService` pass, since both inherently require comparing a file to its siblings). Relationship discovery is deliberately scoped to three explainable types — `sequential_version` (explicit version tokens, or chronological fallback within the same normalized base name), `duplicate_candidate` (identical checksum only — no fuzzy matching), `shared_ownership` (same owner within the same folder) — chained as adjacent pairs within a group (O(n) edges) rather than a full pairwise graph (O(n²)), and groups above 20 files are skipped entirely rather than truncated. This is narrower than the phase spec's full list ("common folders," general "similar naming") by design: an unbounded pairwise similarity graph is exactly the noisy, unexplainable output the phase's own Design Principles ("produce explainable outputs") warn against. Department/time-period inference is similarly conservative — a small keyword dictionary against folder-path segments for department, a direct calendar computation (not an inference) for time period; project/campaign inference is explicitly deferred to Phase 6's AI-assisted classification rather than guessed at with string heuristics likely to be wrong more than they're right.
- **Enrichment is chained from scan completion, not polled or event-bus-driven.** `worker/tasks/scan.py`'s Celery task, after a scan completes successfully, creates an `EnrichmentJob` (`triggered_by=SCAN_COMPLETED`) and calls the enrichment task directly (`run_enrichment.delay(...)`) — both tasks share one Celery app, so this is a plain function call across modules, not a new message-bus abstraction. This chaining logic deliberately lives at the task/orchestration boundary, not inside `ScannerService`, which has no reason to know the Metadata Engine exists at all (Handbook §8's module-boundary contract — a Storage Scanner change should never require touching the Knowledge Engine's code). A manual `POST /v1/connectors/{id}/enrichment` (owner/admin) exists for the phase spec's "reprocessing updated files" QA step, using the identical `EnrichmentJob`/`EnrichmentJobRepository` machinery with `triggered_by=MANUAL`.
- **"Pending" is a live query, not a snapshot.** `FileRepository.list_pending_enrichment_for_connector` returns every `File` with no `FileMetadata` row yet, or whose `scanned_at` is newer than its `FileMetadata.enriched_at` — computed fresh every run rather than recorded at job-creation time. This is what makes an `EnrichmentJob` resumable (an interrupted job's next run just re-queries "what's still pending," no separate touched-file bookkeeping) and makes "reprocess updated files" free (a rescanned file automatically becomes pending again) — the same resumability shape ADR-016's scanner used for a different reason (job-level retry), applied here to job-level resume.
- **Per-file and per-processor failure isolation, mirroring ADR-016's job-level retry distinction.** A processor throwing is caught inside the per-file loop and skipped (logged, contributes nothing) without affecting other processors on that file. A file's extraction/processing throwing an unexpected (non-Drive-connectivity) exception is caught per-file, incrementing `files_failed` and recording an `EnrichmentEvent`, without stopping the rest of the job. Only `DependencyUnavailableError`/`UnauthorizedError` — a whole-connector-affecting condition — propagates to abort the job for Celery's job-level retry, identical to the scanner's reasoning.

**Consequences:** A future contributor adding an eleventh processor or a fourth relationship type should follow the same shape (a pure `FileProcessor.run(context) -> ProcessorResult` for single-file signals, or a method on `RelationshipDiscoveryService` for cross-file ones) — neither needs to know about `EnrichmentService`'s persistence or job-lifecycle code. The AI Gateway does not exist yet and nothing in this phase calls it; Phase 6 (per this phase doc's own "AI Intelligence Layer" framing — see the numbering caveat above) is expected to *add* AI-assisted classification/relationship confidence alongside these deterministic rules, not replace them, per the CTO Note's explicit guidance. `FileExtraction.extracted_text` exists specifically as the future Embedding Engine's input surface (Phase 5 spec's "Search Preparation") — it is deliberately never returned by the backend's file-detail API (`FileExtractionResponse` excludes it) to keep response payloads small, so a future embeddings phase should read it directly via the repository, not expect it to already be flowing through the API layer.

**Alternatives considered:** Running enrichment inline inside the scan job itself (rejected — violates Handbook §6.2's "durable, inspectable handoff" between pipeline stages, and would make a slow enrichment pass block scan-job semantics/retries that have nothing to do with content extraction); a full pairwise relationship graph or broader "similar naming"/"common folder" relationship types as the spec's wording literally suggests (rejected — see Decision; explainability and bounded output were prioritized over spec-literal completeness, consistent with the CTO Note's warning against overreach); snapshotting "files to process" at job-creation time the way Phase 4 initially considered for scans (rejected — a live query is strictly simpler and already gives resumability and automatic reprocessing for free); a heavyweight language-ID library for `LanguageDetectionProcessor` (rejected — "where practical" in the spec read as intentionally lightweight; a small stopword-frequency heuristic over a handful of languages avoids a new ML-flavored dependency for a phase whose whole point is deterministic-first processing).

## ADR-018: AI Intelligence Engine (Phase 6) — AI Gateway abstraction, local-first embeddings, mean-centered similarity, and a stubbed completion provider

**Status:** Accepted

**Context:** [`PHASE_06_FOUNDER_DASHBOARD.md`](phases/PHASE_06_FOUNDER_DASHBOARD.md) (numbering is stale relative to content — this is the AI Intelligence Engine / Semantic Search phase, same class of filename/content mismatch as Phases 3–4) asks for a provider-agnostic embedding and retrieval pipeline, hybrid semantic search, RAG-style context assembly with citations, and conversational querying — built entirely behind "the AI Gateway," with the explicit constraint that "no module outside the AI Gateway may communicate directly with an LLM provider" and that AI cost be minimized by preferring deterministic retrieval. Two decisions were the user's, not Claude's to infer or default: which LLM provider backs the Gateway's `complete()` capability, and how embeddings get generated. The user chose **stub-only for completion** (build the full adapter interface; no real LLM key yet) and **a local, free, offline embedding model** (no API key, no per-call cost, works offline — consistent with the Handbook's no-vendor-lock-in, cost-minimizing philosophy). Both are binding for this phase, not implementation shortcuts to silently reverse later.

**Decision:**
- **`AIGateway` as a thin capability-dispatch class, provider selection at one factory.** `vault_shared.ai_gateway.gateway.AIGateway` exposes exactly two capability methods — `embed(texts)` and `complete(messages, context, max_tokens)` — plus `embedding_model_name`/`embedding_model_version` passthrough properties (so a caller can check "is this file's stored vector current?" without an actual embed call). Both `EmbeddingProvider` and `CompletionProvider` are `typing.Protocol`s, not base classes, matching the pattern already established for `GoogleWorkspaceOAuthClient`. `get_ai_gateway()` (an `lru_cache`d factory) is the *only* place that decides which concrete adapters get wired — `apps/backend` (query embedding + chat) and `apps/worker` (document embedding) both call this factory rather than constructing `AIGateway` themselves, so swapping or adding a provider later is a change to the factory plus a new adapter class, never a change to any caller.
- **Local embedding provider: gensim + pretrained GloVe, not a transformer.** The originally-planned `sentence-transformers`/`torch` stack has zero available wheels on this project's actual development platform (macOS 12.7.6/Monterey, x86_64, Python 3.13) — confirmed via `pip install torch --dry-run` reporting no compatible versions, and `fastembed`/`onnxruntime` equally unavailable. `LocalEmbeddingProvider` (`vault_shared/ai_gateway/providers/local_embedding_provider.py`) instead uses `gensim`'s pretrained `glove-wiki-gigaword-100` word vectors (pure numpy/scipy, real wheels on this platform), averaging a document's stopword-filtered word vectors and unit-normalizing. This is a genuine, long-established semantic-similarity technique (bag-of-word-embeddings), not keyword matching — but it is a materially weaker signal than a modern sentence-transformer, and that tradeoff is accepted explicitly here as a platform-compatibility and zero-cost constraint, not treated as equivalent quality. A `SSL_CERT_FILE` environment workaround (pointing at `certifi`'s bundle) was needed because this platform's stdlib `ssl`/`urllib` — which `gensim.downloader` uses — doesn't trust the system's normal root CAs, unrelated to `requests`/`pip` which bundle their own trust store.
- **Raw cosine similarity on averaged word vectors is a real quality bug, not just a style choice — fixed by stopword filtering plus query-time mean-centering.** Validated empirically against this project's own real, messy Google Drive content (not synthetic test data): raw cosine similarity between any two files' averaged-word-embedding vectors landed between 0.83 and 0.99 regardless of actual topic, because common function words dominate the average and every document ends up clustering around a shared "generic text" direction. Two fixes, both required: (1) stopword removal before averaging (`LocalEmbeddingProvider`'s `_STOPWORDS` set, ~150 common English words) — bumped `_MODEL_VERSION` from `"1"` to `"2"` since this changes what a stored vector *means*; (2) `vault_shared.ai_gateway.similarity.rank_by_similarity` — a lightweight form of the well-known SIF (Smooth Inverse Frequency) correction — mean-centers the query plus its current candidate pool before taking the cosine similarity, computed fresh per search rather than baked into any stored vector (the "shared direction" to remove is a property of *which documents are being compared right now*, not of any single document). Together these took real same-corpus scores from a meaningless 0.83–0.99 band to a genuinely discriminating range (roughly −0.5 to 0.5, unrelated documents clearly separated from related ones) — verified against real re-embedded production data, not just a synthetic check (see Consequences for the bug this surfaced).
- **A caller-visible model-version check on both the pending query *and* the skip-if-unchanged check.** `FileRepository.list_pending_embedding_for_connector` treats a file as pending if it has successful extracted text and (no `Embedding` row yet, or a newer extraction, or the stored `model_name`/`model_version` differs from the currently-configured provider's) — this is what makes changing the embedding algorithm (as the stopword-filtering fix did) automatically queue every previously-embedded file for re-embedding, with no manual migration step. Getting only *this* half right was not sufficient in practice — see Consequences.
- **Hybrid search, not vector-similarity-only.** `SearchService` combines two independent retrieval paths and merges by file id: a plain `ILIKE` substring match across a file's name and the Knowledge Engine's own inferred fields (owner/sharing summaries, naming pattern, knowledge attribute values) — `retrieval_method="metadata"`; and semantic similarity via `rank_by_similarity` over the organization's stored embeddings — `retrieval_method="semantic"`, thresholded at a small positive score to exclude noise. A file found by both is labeled `"both"` with the higher of the two scores. This directly satisfies the phase spec's "avoid relying exclusively on vector similarity" — a literal filename match is often exactly what a keyword search should surface even when embedding similarity is mediocre for short/sparse text.
- **`ContextBuilderService` is a separable, reusable ranking+assembly step**, not folded into `ConversationService`. It takes an already-ranked `list[SearchResult]`, dedupes by file id, merges each file's structured metadata (owner/sharing summary), a short excerpt of extracted content, and up to 3 related-file names (`FileRelationshipRepository`), then stops once a character budget (a rough `4 chars ≈ 1 token` stand-in, since no real tokenizer is wired without a real LLM provider) is exhausted. Kept independent of the conversational flow specifically so a future automation feature (per the phase spec's "reusable context assembly for future automation") can call it directly.
- **`ConversationService` orchestrates retrieval → context → completion → citation persistence, single-turn reasoning with conversation-level history.** Each `ask()` call re-runs `SearchService`/`ContextBuilderService` fresh from the *current* question (not the whole conversation) — this is the phase spec's "single-turn query/response as the baseline capability" — but the full prior message history is still passed to `AIGateway.complete()` so a real LLM provider, once configured, can read follow-ups in context. Conversations are scoped by *user*, not just organization (`ConversationRepository.get_owned` filters on both) — the phase spec's "user-specific conversation history," explicitly not shared/cross-org memory.
- **`ExtractiveCompletionProvider` — the deliberately-stubbed default, never invents an answer.** With no real LLM key configured (per the user's explicit choice), `AIGateway.complete()` is wired to a provider that either returns a clear "I don't have any relevant documents" message (no context retrieved) or assembles a response directly from the already-ranked, already-deduplicated context `ContextBuilderService` produced, clearly prefixed ("No AI model is configured yet...") and labeled with `provider="extractive_fallback"` on every persisted `ConversationMessage` — never silently presented as real LLM reasoning. Swapping in a real provider (Claude, GPT, Gemini) later is a new adapter class plus a two-line change in `get_ai_gateway()`; no caller of `AIGateway.complete()` changes.
- **Brute-force cosine similarity, no vector database.** `EmbeddingRepository.list_for_organization` returns every `(File, Embedding)` pair for an org and `rank_by_similarity` scores them in application code — consistent with Handbook §9/§22's explicit deferral of a dedicated vector store to "Petabyte Scale," not solved speculatively here. `Embedding.vector` is a plain Postgres `ARRAY(Float)`.

**Consequences:** A real bug was caught only by writing an integration test that changed a fake provider's `model_version` between two job runs and asserted the provider's `embed()` was actually called again: `EmbeddingService._embed_file`'s "skip if unchanged" check compared *only* the content hash, not model identity, so a file correctly identified as "pending" by `list_pending_embedding_for_connector` (model-version mismatch) was then silently skipped anyway inside `_embed_file` because its extracted text hadn't changed — the model/version check existed on the query but not on the corresponding skip-check, so it never actually re-embedded anything. This had already happened for real: a prior in-session "460/460 processed, 0 failed" validation of the v1→v2 stopword-filtering fix, run directly against the project's live Google Drive data, was **entirely masked by this bug** — `EmbeddingProgress.files_processed` increments regardless of whether `_embed_file` did real work or returned early, so the job reported full success while every one of the 470 stored vectors silently remained the old, unfiled `model_version="1"`. Querying the real database's `Embedding.model_version` distribution directly (not trusting the job's reported counts) surfaced this before it shipped. `_embed_file` now requires the stored embedding's `model_name` *and* `model_version` to match the currently-configured provider, not just the content hash, before skipping — and a second real re-embedding run against the same live data confirmed 443 real files correctly moved to `model_version="2"`, with `rank_by_similarity` against the newly-genuine v2 vectors reproducing the same good discrimination this ADR's mean-centering section describes. The general lesson: a job's own progress counters are not proof of correctness for what that job's per-item logic actually did — verify against the data the job was supposed to change, not just its self-reported completion status. Separately: `LocalEmbeddingProvider`'s bag-of-word-vectors technique is a real, working baseline, but a materially weaker retrieval signal than a modern sentence-transformer; this is an accepted, explicit tradeoff for zero-cost/offline operation on this platform, not a target quality bar — worth revisiting if/when a wheel-compatible transformer option or paid embedding API becomes acceptable. `ExtractiveCompletionProvider` means no conversation in this phase involves actual LLM reasoning; every "AI Search"/"Chat" answer today is deterministic retrieval dressed as a chat response, which is functionally honest (never fabricates) but not yet what "conversational querying" implies once a real provider is wired in (Phase 7 candidate). Citation "location" is file-level only — no page/line/paragraph anchor — deferred scope, not an oversight.

**Alternatives considered:** `sentence-transformers`/`torch` or `fastembed`/`onnxruntime` for embeddings (rejected — no available wheels on this platform, confirmed via direct install attempts, not merely a size/cost preference); a hosted embedding API (OpenAI, Cohere, etc.) (rejected per the user's explicit "local model, free" choice — no per-call cost, no vendor lock-in, works offline, consistent with Handbook's cost-minimization stance); wiring a real LLM provider now with a placeholder API key (rejected per the user's explicit "stub only" choice — the full adapter abstraction is built and swappable, but nothing should silently call an unconfigured/fake external API); pgvector or a dedicated vector database for similarity search (rejected — same Handbook §9/§22 deferral ADR-016/017 already established: not a problem at this project's current scale); baking the mean-centering correction into each stored vector at embed time (rejected — the "generic direction" to remove is a property of whichever candidate pool a specific query is being compared against right now, not a fixed property of one document, so it has to be computed at query/ranking time); an unbounded relationship/context window with no character budget in `ContextBuilderService` (rejected — unbounded context defeats the point of a token-budget-aware design meant to survive a real LLM's context window later, even though this phase's stub provider doesn't need one strictly).

## ADR-019: Recommendation Engine (Phase 7) — organization-scoped jobs, aggregate-not-per-item recommendations, and a 100%-deterministic rule set

**Status:** Accepted

**Context:** [`PHASE_07_EXECUTION_ENGINE.md`](phases/PHASE_07_EXECUTION_ENGINE.md) (numbering is stale relative to content — this document's own in-text roadmap revision renames it "Founder Command Center & Recommendation Engine," not Execution Engine, same class of mismatch as every prior phase) asks for a Recommendation Engine spanning five categories (storage, knowledge, security, collaboration, productivity) that combines "metadata, knowledge graph, semantic search, AI reasoning (only when necessary), deterministic rules," a Prioritization Engine with an "explainable and configurable" ranking algorithm, and a Founder Command Center dashboard aggregating organization health with historical trend data — explicitly forbidding any recommendation from executing an action or modifying customer data. Three concrete design questions needed resolving that the spec left open: whether a "job" here should be scoped like every prior phase's per-connector jobs or differently; whether a rule should emit one recommendation per affected item (as Phase 5's relationship discovery did) or something coarser; and how "AI reasoning (only when necessary)" cashes out given Phase 6's completion provider is still an explicit stub with no real LLM behind it.

**Decision:**
- **`RecommendationJob` is organization-scoped, the first job type in this codebase that isn't connector-scoped.** Every prior job (`ScanJob`, `EnrichmentJob`, `EmbeddingJob`) belongs to one `StorageConnector`, because each of those stages processes one connector's inventory. The Recommendation Engine and dashboard reason about an *organization's* storage as a whole — "Connected storage providers" (plural) is explicitly one of the Organization Overview's own display fields — so `RecommendationJob.organization_id` is the job's scope, and `RecommendationService.run()` pulls every file across all of an org's connectors in one pass (`FileRepository.list_for_organization_with_details`, extending the org-scoped join pattern ADR-018 already established for embeddings and search). Auto-chaining reflects this: `worker.tasks.embedding._enqueue_recommendation_if_embedding_completed` resolves a just-completed `EmbeddingJob`'s connector back to its organization before creating the `RecommendationJob` — a connector-level event triggering an organization-level job, not a 1:1 chain like every prior stage.
- **No per-item progress table, no cooperative cancellation, no job-level retry — the job type intentionally does *less* infrastructure than its predecessors.** `RecommendationJob` has a plain status lifecycle (`PENDING`/`RUNNING`/`COMPLETED`/`FAILED`) and a single `recommendations_active` result count set at completion, with no `RecommendationProgress` table and no `cancel_requested` column. This is a deliberate proportionality call, not a shortcut: a recommendation run is a single deterministic pass over already-stored data (no per-file external I/O, no per-file wall-clock cost) that finishes in low seconds even at this project's real reference-scale data (~1,000 files) — there is no meaningful "N/M processed" to report mid-run, nothing an external dependency failure could interrupt (same reasoning ADR-018 used to justify `EmbeddingJob` skipping retry), and nothing worth cancelling partway through. `RecommendationEvent` (append-only, mirrors every prior job's event table) still exists for the phase spec's own "Log: Recommendation generation" requirement.
- **Each rule produces at most one aggregate recommendation per organization, never one per affected file.** `Recommendation`'s natural key is `(organization_id, rule_name)`, enforced by a unique constraint — `RecommendationRepository.upsert` either refreshes the existing row for a rule or creates it fresh; there is structurally no way for one rule to produce two rows for the same org. This is the phase spec's own worked example taken literally ("18% of your storage is occupied by duplicate marketing assets" — one sentence about a pattern, not twenty separate "this file is a duplicate" recommendations) and mirrors ADR-017's "bounded and explainable over spec-literal completeness" precedent from the Knowledge Engine's relationship discovery. `affected_file_ids` is a plain JSONB array on the recommendation (no join table), consistent with `FileRelationship.metadata_`'s precedent — a recommendation explaining itself needs to *list* files, not support relational queries from a file back to its recommendations.
- **Recomputable, not accumulating: a rule that stops firing resolves its prior recommendation instead of leaving it stranded.** Every `RecommendationService.run()` computes the full "should be active" set fresh and calls `RecommendationRepository.resolve_stale` for every rule that didn't fire this run — transitioning any previously-`ACTIVE` row for that org/rule to `RESOLVED` (with `resolved_at` set), never deleting it. This is what makes the phase spec's "keep historical data so trends can be visualized over time" and "recomputable after new scans" hold simultaneously: history is preserved (a resolved recommendation is still queryable, e.g. for a future "here's what got fixed" view) while the *active* list only ever reflects what's currently true. Caught by an integration test that changes the underlying data between two runs and asserts the first run's recommendation actually flips to `RESOLVED`, not merely that a second run "succeeds."
- **100% deterministic in this phase — no `AIGateway.complete()` calls anywhere in `RecommendationService`.** The phase spec's "AI reasoning (only when necessary)" is honored by *not* forcing a call to a completion provider that, per ADR-018's binding founder decision, is still `ExtractiveCompletionProvider` — a stub that can't reason, only echo retrieved context. Calling it from every rule evaluation would add latency and complexity for zero actual benefit (no real inference happens) while implying a sophistication the platform doesn't have yet. Instead, `RecommendationRule`/`InsightGenerator` are `typing.Protocol`s — the same interface shape as Phase 5's `FileProcessor` — so a future AI-reasoning-based rule (once a real `CompletionProvider` is wired in per ADR-018's "Phase 7+ candidate" note) can be added as a new class implementing the existing protocol, with zero changes to `RecommendationService`'s orchestration. Eleven rules across the five required categories and two `InsightRecord` generators were implemented this phase — see the Completion Report for the full list and the specific spec examples each one is a documented, bounded approximation of (e.g. "publicly shared" is approximated as `File.is_shared`, since Phase 3/4's scanner never captured Drive's actual permission granularity).
- **The Prioritization Engine is a plain, inspectable weighted sum, not a black box.** `worker/recommendation/priority.py`'s `score_priority` combines confidence, a risk-level weight, a category weight, and a normalized impact ratio via named module-level constants — every input is already a field the founder can see on the recommendation itself (Handbook's "explainable" requirement met by not hiding the inputs, not by exposing the weight coefficients through an API). "Configurable" means a developer edits the constants directly, the same scope every threshold constant in this codebase has had since Phase 5 (no runtime admin UI for weights this phase).
- **`DashboardSnapshot` and `InsightRecord` have different persistence shapes on purpose.** A snapshot is append-only (one row per run, feeding trend charts — Phase 7 spec's explicit ask); an insight is also append-only (a dated observation, not an open issue — no risk level, no suggested action, never resolved) but a `Recommendation` is upsert-with-resolve (an open issue with a lifecycle). Conflating insights with recommendations would force every observational note through an approval-adjacent workflow it doesn't need; conflating snapshots with recommendations would lose the org-wide point-in-time picture a single rule's upsert can't represent.
- **Security-category recommendations are role-filtered at the service layer, not hidden by the frontend.** The phase spec's "Sensitive recommendations should only be visible to authorized roles" is enforced in `RecommendationService.list_for_organization`/`get_owned` (backend) — a member's list request has `SECURITY` category rows excluded server-side, and a direct detail request for one raises `ForbiddenError` (403, not a silent 404) so the caller knows *why*, distinct from a genuine cross-organization access attempt which still 404s. Every detail view is also recorded as an `AuditLog` entry (`recommendation_viewed`), per the phase spec's "All recommendation views should be audited."

**Consequences:** A brand-new organization with only a handful of files gets a `DashboardSnapshot` but zero recommendations — `RecommendationService._generate` skips rule evaluation entirely below `_MIN_FILES_FOR_RULES` (5), since ratio-based signals ("one owner has 50%+ of shared files," "10%+ of files are knowledge-isolated") are meaningless noise at that scale, not a bug to fix. `SearchService`'s pre-existing gap (noted in ADR-018's Consequences — mixed embedding-model-version vectors in ranking) is now also relevant to the Recommendation Engine's `LowRelationshipCoverageRule`/insight generators, which read `Embedding` rows the same brute-force way; not solved here, same deferred status. Recommendations never execute anything and this phase adds no execution surface at all — `requires_approval` defaults to `true` on every row specifically so Phase 8's Approval & Execution System has a field to gate on without a migration, but nothing in this phase reads or acts on it yet. "Publicly shared," "excessive permissions," and "sensitive file exposure" are all approximations of what real Drive permission/content-sensitivity data would show — documented explicitly in each rule's docstring and worth revisiting if a future phase captures Drive's actual per-file ACL detail (not just the `is_shared` boolean Phase 3/4 already store).

**Alternatives considered:** One `Recommendation` row per affected file, matching Phase 5's per-file `FileRelationship` shape (rejected — the phase spec's own example is explicitly aggregate ("18% of storage..."), and a 1,000-file organization with a storage-optimization issue would otherwise produce hundreds of near-duplicate rows the Recommendation Center would have to paginate through instead of showing one clear, prioritized entry); a `RecommendationProgress` table and cooperative cancellation mirroring Scan/Enrichment/Embedding exactly, for consistency (rejected — see Decision; the job type has no per-item work to report progress on or interrupt, and adding the infrastructure anyway would be complexity with no corresponding capability, the same "don't design for hypothetical future requirements" call ADR-018 made for `EmbeddingJob`'s retry policy); connector-scoped `RecommendationJob`s, one per connector like every prior job (rejected — recommendations and dashboard metrics are inherently org-wide per the spec's own "Connected storage providers" display field; a connector-scoped job would either need a separate aggregation step afterward or would only ever describe one connector, contradicting the Command Center's own framing); calling `AIGateway.complete()` for each rule to generate its explanation text in natural language (rejected — see Decision; with only the extractive stub behind it, this would add latency/complexity while producing no real reasoning, and would misrepresent a templated string as AI-generated insight); deleting a `RESOLVED` recommendation instead of retaining it (rejected — directly contradicts the phase spec's "keep historical data so trends can be visualized over time," and a resolved recommendation is exactly the kind of "here's what got better" signal a founder dashboard should be able to show later).

## ADR-020: Execution Engine (Phase 8) — Drive Trash instead of deletion, org-scoped plans reusing the job/rollback machinery, and a narrow rule→action allowlist

**Status:** Accepted

**Context:** [`PHASE_08_SECURITY_RELEASE.md`](phases/PHASE_08_SECURITY_RELEASE.md) (numbering is stale relative to content, same class of mismatch as every prior phase — this document's actual content is the Execution Engine & Human Approval System) asks for a provider-agnostic execution platform that turns an approved `Recommendation` into a deterministic, reviewable `ExecutionPlan`, gates it behind explicit human approval, executes it only through the Connector Platform, verifies the result, and supports rollback where the provider allows it — explicitly forbidding permanent deletion and autonomous/recurring scheduling (Phase 9's content) this phase. Handbook §8.7 already names the Execution Engine as "the only module permitted to perform a mutating action against connected storage" and requires before/after state capture; §13's least-privilege principle says a connector's OAuth scope should be "the narrowest scope that satisfies the current phase's features" — until this phase, that scope was correctly `drive.readonly`, since nothing before Phase 8 ever needed to write. One design question was the founder's, not Claude's to infer: whether any of this phase's own verification work may perform a real mutating call against the founder's actual connected Google Drive account. The founder chose **no real writes — fakes/mocks only**, matching Phases 4-7's precedent of testing worker services against a hand-written fake provider client rather than the real API; this is binding for every test and manual smoke-check in this phase, not just an implementation-time convenience.

**Decision:**
- **The OAuth scope bump to full `drive` (not `drive.file`) happens now, for the first time, and only now.** `google_workspace_scopes` moves from `drive.readonly` to `https://www.googleapis.com/auth/drive` — the narrower `drive.file` scope was rejected because it only grants access to files the app itself created or the user explicitly opened with it, not arbitrary pre-existing files a recommendation might target (e.g. a duplicate file the scanner discovered but this app never touched directly). This is exactly Handbook §13's least-privilege timing rule applied literally: the scope only widens on the phase that actually needs write access, not preemptively on some earlier phase "just in case." A connector authorized before this phase only has `drive.readonly` in its stored `granted_scopes` and must be reconnected before any plan targeting it can be approved — confirmed as a real, live constraint by attempting (and being correctly blocked from) approving a real plan against the founder's actual pre-Phase-8 connector.
- **`ARCHIVE`/`REMOVE_DUPLICATE` are implemented via Drive's own Trash (`trashed: true`), never `files.delete`.** The phase spec is explicit that permanent deletion is out of scope this phase; Drive's trash is soft, founder-recoverable even outside this platform for ~30 days, and — critically — gives both actions genuine, cheap reversibility (`trashed: false` restores exactly what was there) for free, which is what makes `ExecutionPlan.rollback_available` able to default to `true` for every currently-supported action.
- **Execution risk is a distinct dimension from recommendation risk, computed purely from blast radius.** `Recommendation.risk_level` (Phase 7) describes the business/storage risk of the underlying issue; `ExecutionPlan.risk_level` is computed independently from file count alone (≤10 low, ≤100 medium, >100 high) — because every action this phase supports is fully reversible via Drive Trash, the only thing that actually varies in severity between two approvals is how many files one sign-off touches at once. This is also what the frontend's Approval Queue gates its extra high-risk confirmation checkbox on, directly satisfying the phase spec's "make it impossible to accidentally approve high-risk operations."
- **`ExecutionPlan` is organization-scoped, following `RecommendationJob`'s Phase 7 precedent, not connector-scoped like Scan/Enrichment/Embedding.** A plan is derived from an organization-scoped `Recommendation`, so scoping it any other way would require an extra join at every read. `ExecutionJob`, by contrast, is naturally reached through its plan (`execution_plan_id`) rather than needing its own organization-vs-connector design decision.
- **`ExecutionJob.is_rollback` reuses the same job/service machinery for forward execution and reversal, instead of a parallel "RollbackJob" type.** `ExecutionService.run()` branches once on this flag: forward execution iterates `ExecutionStep`s and mutates via the connector; rollback iterates the plan's `RollbackRecord`s in reverse and reverses each mutation (move→move back, rename→restore, un-trash). Both paths share one status lifecycle, the same cooperative cancel/pause flags, the same per-item failure isolation, and the same audit trail — a rollback is not a structurally different kind of job, just a different direction through the same steps.
- **A `RollbackRecord` is created and committed *before* the live Drive mutation it protects against, not after.** Caught during design, not via a failing test: if the record were written after a successful mutation, a failure in that exact window (Drive write succeeds, then the DB write recording it fails or the process dies) would leave a real, already-happened Drive change with no stored way to reverse it. Writing and committing the rollback record first means the worst case is an unnecessary rollback record for a mutation that never happened — harmless — rather than an unrecoverable mutation with no rollback path.
- **Permission validation is two-tier, sharing one function across both processes.** `packages/shared/vault_shared/execution/permission_validation.py`'s `validate_execution_permissions` (connector connected, credentials present, `DRIVE_WRITE_SCOPE` present in `granted_scopes`) is called once by `apps/backend`'s `ApprovalService.decide` at approval time — before a job is even created — and again by `apps/worker`'s `ExecutionService.run` as a defense-in-depth re-check immediately before actually executing, since real time passes between an approval and a worker picking up the job (a connector could be disconnected or scope-downgraded in between). The *other* half of the spec's permission checklist — "resource existence," "current file state" — needs a live Drive read and is therefore worker-only, checked per-step immediately before that step's mutating call, not at plan-creation or approval time when Drive state could still drift before execution actually runs.
- **Layering discipline is unchanged: every live Google Drive call, read or write, happens only in `apps/worker`, never `apps/backend`.** `ExecutionPlanService` builds an entire plan — steps, risk, estimated impact — from already-stored database state with zero Drive calls at plan-creation time, consistent with the pattern every prior phase established (Scanner/Enrichment/Embedding/Recommendation all live in the worker). `ApprovalService`'s permission check reads only stored connector/credential rows, never Drive itself.
- **Only 3 of Phase 7's 11 recommendation rules map to a supported execution action, and the mapping is a narrow, explicit allowlist (`_EXECUTABLE_RULES`), not a generic dispatcher.** `duplicate_files`→`REMOVE_DUPLICATE`, `archive_candidates`/`large_unused_files`→`ARCHIVE`. Every other rule (all of security, collaboration, productivity, and the two knowledge-optimization rules) has no concrete, safe mutation defined yet and is rejected with a clear `ValidationError` naming the rule if a plan is attempted — "this category is view-only for now" is a deliberate, documented boundary, not a bug waiting to be closed. `MOVE_FILE`, `MOVE_FOLDER`, `RENAME`, and `UPDATE_METADATA` action types are fully implemented end-to-end in the connector and execution service (per the phase spec's literal action list) but are not yet reachable from any real rule — built ahead of use intentionally, since the spec names them explicitly, but not wired to anything that would let a plan actually request one yet.
- **Approval is single-decision-terminal this phase; "multi-step approvals" is explicitly future-ready, not built.** One `ApprovalRequest` resolves to exactly one `ApprovalDecision` (`approve`/`reject`/`request_changes`, all terminal) — a rejected or changes-requested plan is not reopened. A founder wanting to try again gets a fresh plan via a new `POST /v1/execution-plans` call, since the recommendation itself stays `ACTIVE` and `has_active_plan_for_recommendation` only blocks while a plan is still in flight, not permanently.
- **No autonomous or recurring execution exists anywhere in this phase.** Every execution starts from one human's `approve` decision (`ApprovalService.decide` is the only code path that ever creates an `ExecutionJob` for forward execution); there is no scheduler, no cron-like trigger, and no auto-chaining into execution the way every earlier stage auto-chains into the next (scan→enrich→embed→recommend). This is a hard boundary per the phase spec, reserved for Phase 9.

**Consequences:** Because every currently-supported action is Drive-Trash-based, this phase's rollback story is simpler and more uniformly reversible than a hypothetical "some actions can't be undone" design would have been — but that simplicity is a direct consequence of the narrow action allowlist above, not a general property of the Execution Engine; the day a rule needs a truly irreversible action, `ExecutionPlan.rollback_available` will need to become per-step rather than per-plan. Every connector authorized before this phase must be reconnected before any execution plan targeting it can be approved — a real, disruptive-sounding migration step, but a deliberate and correctly-timed one per Handbook §13, not an oversight; verified live against the founder's actual pre-Phase-8 connector, which was correctly and safely blocked from approving. The founder's binding "no real writes" testing constraint means this phase's confidence comes from two independent sources that were kept deliberately separate: real HTTP calls against the real backend and real Postgres data for everything that only reads or writes this platform's own database (plan creation, listing, the permission-check-blocks-approval path, a real reject decision), and a hand-written fake Drive client for every code path that would otherwise call Google (trash/un-trash, verification, rollback) — nothing in this phase's own development process ever mutated the founder's actual Drive content; the founder's own first real approval, once a connector is reconnected with write scope, will be this platform's first genuine mutating call. `Recommendation.affected_file_ids` being raw UUIDs (a Phase 7 gap already logged) now also means `ExecutionStep.target_file_id` inherits the same "no enriched file name/path in the API response for a UUID a human has to interpret" limitation on the Plan Viewer.

**Alternatives considered:** `files.delete` for `ARCHIVE`/`REMOVE_DUPLICATE`, matching their names more literally (rejected — the phase spec explicitly forbids permanent deletion this phase, and Trash gives the same practical outcome — the file leaves the founder's normal view — with genuine recoverability); bumping the OAuth scope to full `drive` back in Phase 3 when the connector was first built, to avoid a reconnection step now (rejected — directly violates Handbook §13's least-privilege timing, and would have granted write access for five phases with nothing in the codebase that could or should have used it); a separate `RollbackJob` model/table distinct from `ExecutionJob` (rejected — a rollback is a different direction through the same steps, not a structurally different kind of work; a second model would duplicate the entire status/cancel/pause/audit lifecycle `ExecutionJob` already has for no real benefit); connector-scoped `ExecutionPlan`s mirroring Scan/Enrichment/Embedding (rejected — a plan is derived from an org-scoped `Recommendation`; scoping it to a connector instead would need an extra join at every single read for no corresponding benefit, the same reasoning ADR-019 used for `RecommendationJob`); a generic, config-driven rule→action mapping that any future rule could opt into without a code change (rejected — three rules is not enough evidence to justify a generic dispatch layer yet; an explicit allowlist that fails loudly and specifically for an unmapped rule is more honest about the current, narrow scope than a generic mechanism would be); real end-to-end verification against the founder's actual connected Drive account during development (rejected per the founder's explicit, binding choice — fakes/mocks only, exactly like every prior phase's worker-service testing pattern, so nothing in this phase's own build process could accidentally mutate real customer-equivalent data before the founder chooses to trigger it themselves through the UI).

## ADR-021: Automation Engine (Phase 9) — policies as a second kind of approver, promoting Execution Engine services to packages/shared, and a DB-polled scheduler

**Status:** Accepted

**Context:** `PHASE_09.md` asks for a workflow orchestration platform — a node-graph Workflow Builder, scheduled/event/manual triggers, a Policy Engine that "determines execution behavior," a workflow execution engine with retry/resume/branching, seamless integration with Phase 8's Approval System, a Notification Framework, starter templates, and draft/published/version-history workflow versioning — explicitly forbidding the Workflow Engine from ever bypassing the Approval System or the Connector Platform. The Core Philosophy frames automation as "structured execution of approved business policies," not autonomous intelligence — "should feel like a dependable team member... not an unpredictable autonomous agent." Two concrete questions had no spec answer and were the founder's, not Claude's, to decide (mirroring ADR-018's LLM-provider and ADR-020's real-writes precedents): whether any policy may let an `EXECUTE_ACTION` node run without a per-instance human approval click, and whether the new Notification Framework's email channel should send real email. The founder chose **policy-gated auto-execution allowed** (a published, owner/admin-authored policy may auto-approve, but creating/publishing that policy itself always requires a human, and every auto-execution still produces the exact same audited `ApprovalDecision` a human's click would) and **email stays a stub** (same "build the full adapter, stub the external call" pattern ADR-018 used for the LLM completion provider). Both are binding for this phase.

**Decision:**
- **Automation never bypasses the Approval System — a published `WorkflowPolicy` becomes a second, non-human *kind* of approver, not a shortcut around approval.** `ApprovalDecision` gains `decided_by_policy_id` (nullable, alongside the existing nullable `decider_user_id`, with a CHECK constraint requiring exactly one) — `ApprovalService.auto_decide_via_policy` produces a decision, an `ExecutionJob`, and the same execution-audit trail `decide()` does for a human, just attributed differently. A policy's `SKIP` effect means the `EXECUTE_ACTION` node never even builds a plan for a run where the policy doesn't want to act; `REQUIRE_APPROVAL` means the plan is built and a real human-decided `ApprovalRequest` gates it, identical to Phase 8's manual flow. This is what makes the phase spec's "no bypass" requirement literally true rather than just documented intent.
- **`ExecutionPlanService` and `ApprovalService` moved from `apps/backend/app/application/` into `packages/shared/vault_shared/execution/`**, because Phase 9's `EXECUTE_ACTION` workflow node — running in `apps/worker` — needs to build plans and decide approvals directly, not just the backend's REST endpoints. Same "promote to `packages/shared` once a second app needs it" reasoning ADR-015 used ahead of Phase 4 for the DB layer. `ApprovalService`'s two Celery-enqueue side effects are constructor-injected callables rather than an import of either app's producer module — `apps/backend`'s thin `ApprovalService` subclass injects its real `app.infrastructure.queue.*` functions; `apps/worker`'s `WorkflowExecutionService` injects plain `celery_app.send_task(...)` closures. Neither app imports the other's code; the backend's existing `ApprovalService(db)`/`ExecutionPlanService(db)` call sites needed zero changes, verified by rerunning the entire pre-existing Phase 8 test suite (251 tests) unmodified and green after the move.
- **`ApprovalRequest`'s CHECK constraint requires *at least one* of `execution_plan_id`/`workflow_node_execution_id`, not exactly one.** The first draft of this schema (during this phase's own development, caught before any consumer code existed) assumed the two were mutually exclusive — a plan-only approval (Phase 8's original shape) or a workflow-node-only approval (a plain `APPROVAL` node with nothing to execute). That's wrong for the actual common case: a workflow's own `EXECUTE_ACTION` node needing human sign-off creates a real `ExecutionPlan` *and* needs deciding it to resume the paused `WorkflowExecution` — both columns are set on the same row, and `ApprovalService.decide()` performs each side effect independently (create a job if a plan is attached; resume the workflow if a node execution is attached) rather than as an either/or branch. Caught and fixed via the same downgrade/edit/reapply migration cycle ADR-020 used, before any worker code depended on the schema.
- **The Workflow Builder submits a whole node graph per save, not incremental per-node edits.** `WorkflowNode` rows are real, queryable rows (per the phase spec's own DB entity list, not a JSONB blob) linked by a JSONB `next_nodes` outcome→node-id map living on the node that owns the edge — but the API accepts client-assigned string `key`s for cross-referencing (real ids don't exist until after insert) and `WorkflowService.replace_nodes` translates keys to real ids in a two-pass insert-then-update, mirroring the same key-remapping `_clone_nodes` uses when `get_or_create_draft`/`clone` copy an existing graph. Only a `DRAFT` version's nodes are ever mutable; a `PUBLISHED` version is frozen the moment an execution may have referenced it.
- **`WorkflowVersion` and `WorkflowPolicy` both use the "at most one active row, enforced at the service layer" pattern** `Recommendation`'s natural-key upsert and ADR-019 already established, applied twice more: publishing a `WorkflowVersion` supersedes whatever was previously published for that workflow (and republishing an old `SUPERSEDED` version is literally what "rollback" means — no new version created, no nodes copied); publishing a `WorkflowPolicy` archives whatever was previously published for that `policy_key` (`WorkflowPolicyRepository.create_draft` always appends the next version number for a key, full history retained, never an in-place update).
- **The scheduler is a custom `croniter`-based sweep polling a `SchedulerJob` table, not Celery Beat's native per-task crontab schedules.** Celery Beat's own schedule is static application config, read once at Beat-process startup — it has no mechanism for a workflow trigger created or edited through the API at runtime to take effect without restarting the Beat process. Instead, one *fixed* Celery Beat entry (`worker.scheduler.sweep`, every 60s) claims every due `SchedulerJob` row via a single atomic `UPDATE ... WHERE next_run_at <= now() ... RETURNING` (`SchedulerJobRepository.claim_due`) — this is what prevents the phase spec's named "trigger duplication" failure mode if more than one Beat/worker process is running — fires a `WorkflowExecution` for each, and recomputes/persists the next occurrence via `croniter`, interpreted in the configurable `SCHEDULER_TIMEZONE` (independent of Celery's own always-UTC broker timezone). A claimed row that was never rescheduled would silently stop firing forever, so rescheduling always runs, even when firing itself was skipped (paused workflow, no published version) or failed.
- **`WorkflowPolicy.conditions` gate at the recommendation level (file-count ceiling, confidence floor), not per-file inclusion/exclusion.** The phase spec's own examples ("skip actions on executive folders," "never modify legal documents") describe per-file filtering, which would require `ExecutionPlanService.create_plan` itself to accept a file-exclusion parameter — a real change to Phase 8's already-tested plan-building logic. This phase's `_policy_matches` instead evaluates `max_affected_files`/`min_confidence` against the aggregate `Recommendation` a matching `EXECUTE_ACTION` node would act on — a real, working, but coarser gate; a documented scope boundary; see the Phase 9 completion report.
- **Only 4 of the phase spec's 7 named event triggers are wired to a real firing hook this phase: `scan_completed`, `enrichment_completed`, `recommendation_generated`, `connector_reconnected`.** Each is a one-line addition at an already-existing completion boundary (`worker/tasks/scan.py`, `enrichment.py`, `recommendation.py`, and the backend's `ConnectorService.complete_connect`), calling the new shared `vault_shared.workflow_events.fire_workflow_event` — itself promoted to `packages/shared` for the same cross-app reason as `ApprovalService`, since `connector_reconnected` fires from the backend while the other three fire from the worker. `file_added`, `file_updated`, and `storage_threshold_exceeded` are modeled as valid, configurable `WorkflowEventType` values (a founder can create a trigger for one today) but have no real firing hook — the scanner doesn't currently distinguish an added file from an updated one as separate signals, and no existing job computes an aggregate storage-threshold check. Documented, not silently missing.
- **Every execution still traces back to a human, a clock, or an already-happened event — never a fully unattended, self-originating decision.** A `WorkflowExecution`'s `trigger_type` is always exactly one of `manual` (a human clicked), `scheduled` (the sweep's own claim, itself only possible because a human published both the workflow and its trigger), or `event` (a real prior pipeline stage completed). Nothing in this phase invents a trigger a human didn't configure.

**Consequences:** Two real, non-cosmetic bugs were caught by the automated test suite before this phase was considered done, not found live: (1) the `ApprovalRequest` exactly-one-target CHECK constraint above, caught during design before any worker code existed against it; (2) a node that returns the internal "waiting" sentinel (an `APPROVAL` node pausing, or a `DELAY` node scheduling its countdown) never actually transitioned `WorkflowExecution.status` to `PAUSED` — it silently stayed `RUNNING` — caught by `test_approval_node_pauses_then_resumes_on_the_correct_branch` asserting the status directly, not just that the run eventually completed; both are fixed and covered by regression tests, but the second one specifically would have broken the frontend's pause/resume button logic (which branches on exactly `running` vs. `paused`) had it shipped. Schedule accuracy is bounded by the sweep interval (currently 60s), not exact-to-the-second — acceptable for the phase spec's own examples (daily/weekly reports, periodic archive runs), revisit if a future use case needs sub-minute precision. `packages/shared` now contains two classes (`ExecutionPlanService`, `ApprovalService`) whose business logic originated in `apps/backend` and one new module (`vault_shared.workflow_events`) that both apps call into — this is the second time a "promote once a second app needs it" move has happened (ADR-015 was the first, for the DB layer itself), and is worth watching as a recurring signal that more of `apps/backend/app/application/` may eventually belong in `packages/shared` rather than staying backend-only.

**Alternatives considered:** Having the worker call the backend's REST API over HTTP for plan-creation and approval-decision instead of importing shared code (rejected — this codebase has no precedent for worker→backend HTTP calls at all, only backend→worker via Celery; adding one now for two operations would introduce a new communication pattern, new auth requirements for an internal service-to-service call, and network failure modes, all avoidable by promoting the already-layering-clean business logic instead); a fully autonomous "no human ever configured this" scheduling mode (rejected outright per the Core Philosophy's explicit "not an unpredictable autonomous agent" framing and the founder's own choice — every automated path still traces back to a human-authored workflow, trigger, and policy); Celery Beat's native `crontab` schedule entries generated dynamically and reloaded on every workflow-trigger change (rejected — would require either restarting the Beat process or building a custom Beat scheduler backend, both heavier than a 60-second DB-polled sweep for this project's scale); per-file policy conditions wired directly into `ExecutionPlanService.create_plan` this phase (rejected — a real change to already-tested Phase 8 logic for marginal benefit at this stage; deferred, not forgotten); a blanket "email notifications enabled" toggle that actually sends through some default provider (rejected per the founder's explicit binding choice — the toggle exists in settings for future use, but flipping it does not and must not cause a real email to be sent this phase, since no real provider is configured).

## ADR-022: Production Hardening (Phase 10) — stub-until-configured observability, a DB-polled cache instead of a new subsystem, and an IaC reference implementation validated but never applied

**Status:** Accepted

**Context:** `PHASE_10.md` asks for the platform to become production-ready across nine simultaneous fronts — security hardening, performance, reliability, observability, logging, backup/DR, deployment automation, infrastructure-as-code, and a completed CI/CD pipeline — plus a full documentation set (Deployment Handbook, API/Architecture/Database Documentation, Security Guide, Operations Runbook, Disaster Recovery Guide, Monitoring Guide, Contributor Guide, Release Notes, a V1 User Guide, and compliance-readiness notes) and a Release Readiness Report as the phase's own deliverable. Unlike every prior phase, this one adds almost no product code — its job is to make Phases 1-9's product code trustworthy to run for a real customer. No founder decision was required this phase (unlike ADR-018's LLM provider, ADR-020's real-writes gate, or ADR-021's auto-execution/email choices) — every open question here was an engineering judgment call about *how* to harden, not *whether* something risky should be allowed to happen.

**Decision:**
- **Every new external integration (Prometheus/OpenTelemetry/Sentry) follows the same "stub until configured" shape ADR-018 established for the LLM provider and ADR-021 established for email — off by default, a no-op until a real endpoint/DSN is set, never a hard dependency.** `vault_shared.tracing.configure_tracing()` and `vault_shared.error_tracking.configure_sentry()` both check an environment variable (`OTEL_EXPORTER_OTLP_ENDPOINT`, `SENTRY_DSN`) and return immediately if unset — OpenTelemetry's own default global `TracerProvider` is already a documented no-op, so every `FastAPIInstrumentor`/`SQLAlchemyInstrumentor`/`CeleryInstrumentor` call in this codebase is unconditional and safe to make regardless of whether tracing is actually configured. Prometheus is the one exception that's always-on rather than stubbed: `/metrics` (backend) and `worker/metrics_server.py` (worker) always expose real data, because a metrics *endpoint* existing costs nothing until something scrapes it, unlike an LLM call or an email send.
- **Custom Celery task headers must never be named `correlation_id`.** The correlation-ID propagation design (`app/infrastructure/queue/correlation.py`'s `vault_request_id` header, extracted in `worker/observability.py`) originally used `correlation_id` as the header key, matching common industry convention — but Celery's own AMQP message protocol already reserves that exact name as a built-in `Context` property, always equal to the task's own ID, used for RPC-style result-backend matching. `Context._get_custom_headers` strips any header key that collides with one of `Context`'s own reserved attributes before a task ever sees it, so the custom value was silently discarded and replaced by the task ID every time — caught only by running a real Celery worker against real Redis and grepping its structured log output for the literal string sent, not by unit tests (a mocked Celery message never exercises the real protocol-merge/strip behavior). Renamed to `vault_request_id`, verified the same way afterward.
- **The dashboard cache is Redis-backed, per-organization-keyed, TTL-only invalidation — no explicit cache-busting on write.** `/v1/dashboard` (the phase spec's own named example under "Dashboard aggregation") now checks `dashboard:{organization_id}` in Redis before calling `DashboardService`, and writes the serialized `DashboardResponse` back with a 30-second TTL (`dashboard_cache_ttl_seconds`) on a miss. No signal from any scan/enrichment/embedding/recommendation job invalidates this early — the underlying data changes at most once per pipeline run (minutes, not seconds), so a bounded staleness window is a simpler and equally-correct trade than wiring cache invalidation into four different job-completion paths for a page that already polls. `get_cached_json`/`set_cached_json` fail open on a Redis error, the same defensive posture `rate_limit.py` already established — a cache must never be the reason an endpoint goes down.
- **A circular Terraform module dependency was found and fixed before this phase's infrastructure code was considered done: `compute` → `secrets` → `database`/`redis` → `compute`.** The `database` and `redis` modules' security groups needed to allow ingress from the ECS tasks' security group, and the natural place to define that security group seemed to be the `compute` module (it owns the ECS services) — but `compute` also needs `secrets.secret_arns`, and `secrets` needs `database`/`redis` connection strings, closing the cycle. Fixed by moving `aws_security_group.ecs_tasks` into the `network` module instead — the one module every other module already depends on for VPC/subnet IDs — so `database`, `redis`, and `compute` all just reference `network.ecs_tasks_security_group_id` as a plain input with no dependency on each other. Caught by actually installing Terraform (`brew install hashicorp/tap/terraform` — not preinstalled in this environment) and running `terraform validate` against the full module graph, not by manual review; the same pass also caught and fixed a missing S3 lifecycle-rule `filter` block and an AWS-provider-version-mismatched `data.aws_region` attribute (`.region` only exists on provider v6+, but `environments/*/providers.tf` pins `~> 5.0`).
- **The reference cloud target is AWS (ECS Fargate, RDS, ElastiCache, ALB, S3, Secrets Manager, CloudWatch), chosen once and implemented fully rather than left abstract.** The phase spec's own "cloud-provider aware but not tightly coupled" instruction is satisfied at the *module* boundary (network/database/redis/storage/secrets/compute/load_balancer/monitoring, each a swappable unit) rather than by writing pseudo-code with no real provider at all — a founder who ends up on GCP or Azure rewrites `infrastructure/terraform/modules/*`, not `apps/*`. Every module and both environments (`staging`, `production`) pass `terraform fmt` and `terraform validate` with zero errors; nothing has been applied against a real AWS account, since none exists in this environment — the same "validated, never live-verified against the real external system" honesty this codebase already applies to Google Drive writes before a founder reconnects with real credentials.
- **CI's `deploy`/`rollback` jobs are real, complete automation gated behind a `workflow_dispatch`-only trigger plus a GitHub Environment approval — never triggered by a push or PR.** They build+push images, run `terraform apply`, and smoke-test the result (`infrastructure/scripts/smoke_test.sh`, live-verified locally against a running backend) — but they reference secrets (`CONTAINER_REGISTRY`, cloud credentials) that don't exist in this repository yet, so a dispatch today fails at the first step that needs one, which is the correct and safe failure mode until a founder actually configures a target environment.
- **A real backup/restore drill was run against the founder's own local Postgres, not simulated.** `infrastructure/scripts/backup.sh` (`pg_dump -Fc`) and `restore.sh` (`pg_restore --clean`) were used to back up the real local `vault` database (49 tables, tens of thousands of rows accumulated across nine phases of development and testing), restore into a disposable `vault_restore_drill` database, and diff every table's row count between source and restore — all 49 matched exactly. The throwaway database was dropped immediately after; nothing about the founder's real local data was altered. `backup.sh`'s retention-pruning logic was written with `mapfile` initially and had to be rewritten without it after failing on this machine's actual `/bin/bash` (3.2, macOS's GPLv3-driven ceiling) — a real portability bug caught by running the script, not by review.
- **Dependency vulnerability scanning found and fixed two real CVEs already present in the codebase before this phase started scanning for them:** `cryptography` 49.0.0 (CVE-2026-69247, a PKCS7 decrypt timing/error oracle — not reachable through this codebase's Fernet-only usage, but bumped to 50.0.0 anyway) and `pypdf` 5.9.0 (a long run of CVEs, fixed by the 6.14.2 floor — a major version bump whose extraction-code API surface (`PdfReader`) turned out to be unchanged, verified by rerunning the worker's extraction test suite). Both were found by installing and running `pip-audit` directly (not previously part of this project's toolchain) against the real `requirements.txt` files, and are now permanent CI gates via the new `security` job.

**Consequences:** This phase's infrastructure code (Terraform, CI deploy job, Docker non-root users, the worker metrics multiprocess sidecar) is the first in this project that cannot be live-verified end-to-end in this environment — no Docker daemon, no AWS account. Every piece was validated as strongly as the environment allows (`terraform validate`, `docker compose config`, `ruff`/`mypy`/full test suites) and documented honestly as "validated, not applied" rather than claimed as tested; a founder with a real cloud account and a running Docker daemon is the first one who can actually exercise the deploy path, the container builds, and the local monitoring stack (`docker-compose.monitoring.yml`). The worker's Prometheus metrics require `PROMETHEUS_MULTIPROC_DIR` to be set identically across every worker replica and the dedicated `metrics_server.py` process reading from it — correct and documented, but a real operational detail a founder must get right when standing up a multi-replica worker fleet (a single-replica or `solo`-pool local dev setup works without this caveat). `packages/shared` grew two more cross-cutting modules (`metrics.py`, `tracing.py`, `error_tracking.py`) used identically by both apps — a third instance of the "promote once both apps need it" pattern ADR-015 and ADR-021 both already established, worth continuing to watch as a recurring signal.

**Alternatives considered:** A custom in-house metrics/tracing solution instead of Prometheus/OpenTelemetry (rejected — the phase spec names these specific tools, and they're the de facto standard this platform's eventual customers' own ops teams will already know); eagerly invalidating the dashboard cache from every job-completion signal instead of a bounded TTL (rejected — four separate call sites for a page that already polls, for a staleness window measured in seconds against a data source that changes in minutes, is complexity without a proportional benefit); Kubernetes/EKS instead of ECS Fargate for the compute layer (rejected — ECS Fargate needs no cluster-management surface of its own, a better fit for a founder who isn't hiring a platform team yet; nothing about the module boundaries below `compute/` assumes ECS specifically, so this is revisitable later); committing to a specific secondary cloud provider's Terraform alongside AWS's "to prove portability" (rejected — writing and never validating a second, unused implementation would be worse than writing one real one, per this ADR's own "validated, not applied" standard); skipping `pip-audit`/`pnpm audit` in CI to avoid occasional false-positive noise (rejected — both scans found genuine, fixable vulnerabilities on their very first real run in this codebase; `ignore-unfixed` on the Trivy image scan is the one deliberate noise-reduction exception, since failing CI over a CVE with no available fix is not actionable).

## ADR-023: Storage Intelligence Layer (Phase 1 post-hardening) — checksum-direct duplicate detection decoupled from enrichment, live queries over persisted per-file listings, and set-union savings

**Status:** Accepted

**Context:** A "Storage Intelligence Layer" spec asked for duplicate detection, a storage analyzer (totals/breakdowns by type/size/source), large/old/inactive-file detection, temporary-file heuristics, a centralized non-double-counting savings calculation, an API surface (`/v1/storage/*`), and a dashboard — explicitly detection/analysis/recommendation only, no execution. The codebase already had a checksum-based duplicate *signal* (Phase 5's `FileMetadata.duplicate_group_key`, aggregated into one `Recommendation` row by `DuplicateFilesRule`) and staleness rules (`ArchiveCandidateRule`, `LargeUnusedFilesRule`), but neither exposes a browsable, paginated, per-group/per-file surface — the Recommendation Engine's `(organization_id, rule_name)` identity (ADR-019) deliberately collapses an entire org's duplicate problem into one advisory row, not a structure a dashboard can page through, sort, or link a stable URL to. Three design questions needed resolving: whether to reuse `duplicate_group_key` (enrichment-owned, Phase 5) or compute groups independently; whether large/old/inactive file *listings* (as opposed to counts) belong in a persisted table or a live query; and how to guarantee a file counted as both a duplicate and a temporary-file candidate is never double-counted in "potential savings."

**Decision:**
- **Duplicate detection reads `File.checksum` directly via a DB-side `GROUP BY`, never `FileMetadata.duplicate_group_key`.** `duplicate_group_key` is enrichment-owned (Phase 5, ADR-017): it's only populated after that connector's enrichment job's relationship-discovery pass has run, and it's capped at 20-member checksum groups for relationship-graph reasons unrelated to storage accounting. A dedicated storage-intelligence duplicate detector has no reason to wait behind enrichment/embedding/recommendation or to inherit a cap designed for a different consumer, so `FileRepository.list_duplicate_checksum_groups_for_organization` groups directly on `File.checksum` (`GROUP BY checksum HAVING count(*) > 1`, org-scoped via the same `storage_source → storage_connector.organization_id` join every other cross-connector query uses) — the spec's own "candidate optimization" (avoid O(n²)) is satisfied natively, since checksum equality already implies size equality, making a separate size-prefilter stage redundant rather than an optimization. This is why `StorageAnalysisJob` chains directly off `ScanJob` completion (`worker/tasks/scan.py::_enqueue_storage_intelligence_if_scan_completed`, a sibling of the existing enrichment chain, not a successor of it) rather than off `RecommendationJob` as originally suggested — storage intelligence has no real dependency on the enrichment/embedding/recommendation chain at all.
- **`DuplicateGroup` is upserted by `(organization_id, checksum)`, mirroring `Recommendation`'s upsert-by-identity-key convention (ADR-019) — but membership is fully replaced, not soft-resolved.** A group's `id` stays stable across re-analyses (so a bookmarked `/v1/storage/duplicates/{id}` link keeps working), but `DuplicateGroupMember` rows are deleted and reinserted every run, and a checksum that no longer has ≥2 files is deleted outright (`DuplicateGroupRepository.delete_groups_for_organization_not_in`) rather than marked resolved. Recommendation's soft-resolve exists so a founder can see "this used to be flagged" — that audit narrative doesn't apply to a pure derived fact like group membership, so the simpler, fully-correct-on-every-run delete-and-recreate was chosen over carrying `Recommendation`'s pattern where it doesn't fit.
- **Large/old/inactive/temporary-candidate *listings* are live, paginated SQL queries against `FileRepository`, never persisted per-file — only the aggregate counts/bytes are persisted, on `StorageAnalysisSnapshot`.** Per-file rows for these categories are cheap to derive on demand (indexed range queries on `size_bytes`/`provider_modified_at`/`provider_viewed_at`, proven fast at real reference scale — see Consequences) and change continuously as new scans land; persisting them would mean either a second job pass to keep them current or silently stale listings between analyses. Only `DuplicateGroup`s are persisted at the per-item level, because duplicate grouping is a genuine O(n) aggregation worth caching, and because the "recommended keep file" reasoning needs a stable place to live.
- **The Storage Analyzer's breakdowns (by type/size-bucket/source) and the candidate *counts* are computed in one Python pass over `FileRepository.list_all_for_organization`, inside the background job — never in the request path.** This mirrors the Recommendation Engine's `list_for_organization_with_details` and `EmbeddingRepository.list_for_organization` (ADR-018/19) "load the org once, aggregate in Python" acceptance: it's O(n), not O(n²), and running inside a Celery task means there's no user-facing latency to protect (the exact class of mistake the Search Performance investigation found and fixed — an expensive operation blocking a live request — deliberately avoided here by construction, not by afterthought). Measured against this project's real reference-scale organization (1,029 files, 12 duplicate groups found), the entire job — duplicate detection, full-org fetch, breakdown aggregation, candidate counting, savings computation, and snapshot persistence — completed in 0.52 seconds.
- **The Savings Engine deduplicates by `file_id` set intersection, computed from already-persisted data, not two independently-summed totals.** `SavingsAnalyzer.analyze` reads the real recoverable-file-id set back out of `DuplicateGroupMember` (`is_recommended_keep = false`) and subtracts it from the temporary-candidate id set before summing the remainder — a file matching both categories contributes its bytes exactly once. This is deliberately a numeric identity check (`file_id` set operations), not a heuristic — the one place in this phase where "avoid double counting" had to be literally, not approximately, true. Confirmed against real data: this organization's duplicate-recoverable (17,287,885 bytes) + temporary-candidate (577,949,179 bytes) totals sum to 595,237,064 bytes independently, but the persisted `total_potential_savings_bytes` is 594,331,933 — the 905,131-byte difference is a real file counted once instead of twice.
- **Duplicate "recommended keep" reasoning is two independent, named signals (location structure, recency), not recency alone.** The spec explicitly forbids "newest = correct" as the sole heuristic; `_recommend_keep` scores each candidate on whether its path avoids Downloads/Desktop/Temp-like segments and on `provider_modified_at` recency, reports which signals agreed, and emits a confidence (0.86 when both agree, down to 0.4 when neither strongly does) alongside a human-readable reason string — never a bare "these files are duplicates," and never a claim of certainty the two-signal heuristic doesn't support.

**Consequences:** Only Google Drive's own `md5Checksum` is ever compared — native Google Docs/Sheets/Slides (which Drive never returns a checksum for) are structurally excluded from duplicate detection rather than falsely reported as unique or compared some other way, consistent with the spec's "mark appropriately instead of falsely claiming uniqueness." Storage totals/breakdowns and candidate counts reflect the *last analysis*, not the current instant — `StorageOverviewResponse`'s `last_analyzed_at`/`last_analysis_status` fields exist specifically so the frontend can show that staleness honestly rather than implying a live number. The duplicate-detection upsert (`DuplicateGroupRepository.upsert_group`) is a SELECT-then-conditionally-INSERT, not a native `INSERT ... ON CONFLICT` — safe under the current architecture (a `StorageAnalysisJob` is guarded against a concurrent duplicate run by `has_active_job`, the same pattern `RecommendationJob`/`EnrichmentJob` already use), but not itself SQL-atomic against a true concurrent race, a gap explicitly surfaced rather than silently assumed away. Large/old/inactive/temporary-candidate browsing pages (only the duplicate-groups list/detail got a dedicated frontend page this phase) are a natural, low-risk follow-up — their backend endpoints already exist and are already paginated, org-scoped, and tested.

**Alternatives considered:** Reusing `FileMetadata.duplicate_group_key` directly instead of a fresh checksum `GROUP BY` (rejected — see Decision; would gate storage intelligence behind enrichment completion and inherit a 20-member cap designed for a different consumer); persisting large/old/inactive/temporary-candidate file listings the same way duplicate groups are persisted (rejected — these are cheap, continuously-changing indexed range queries, not an O(n) aggregation worth caching; persisting them would need a second freshness-tracking mechanism for no accuracy benefit); chaining `StorageAnalysisJob` off `RecommendationJob` completion, matching the spec's literal pipeline diagram (rejected — the two engines share no real dependency once duplicate detection reads `File.checksum` directly instead of `duplicate_group_key`, and chaining behind three prior stages would add minutes of latency to a computation that itself takes half a second); a single combined "savings total" per category without file-id-level deduplication, trusting each category's own count to already be mutually exclusive (rejected — nothing guarantees that, and the real-data measurement above shows the overlap is real, not theoretical); "newest file wins" as the sole keep-recommendation signal (rejected — explicitly forbidden by the spec, and demonstrably wrong in practice: a stale copy re-saved into a Downloads folder can have a newer timestamp than the actual canonical copy in a structured project directory).

## ADR-024: AI Storage Assistant — extending "Ask Vault" with deterministic tool routing over Storage Intelligence, reusing the existing completion-provider settings for OpenRouter/GLM

**Status:** Accepted

**Context:** A spec asked for an "AI Storage Assistant" answering natural-language storage questions ("How much storage am I using?", "Show me duplicates") using real backend data, read-only, token-budget-conscious, via Z.ai's GLM through OpenRouter, with an explicit "provider abstraction" requirement and its own env var naming (`AI_PROVIDER`, `AI_MODEL`, `OPENROUTER_API_KEY`). Inspection found a mature "Ask Vault" conversation system already shipped (Phase 6): `Conversation`/`ConversationMessage`/`Citation` models, user-*and*-org-scoped ownership (`ConversationRepository.get_owned`), `ConversationService.ask()` (retrieval → context assembly → `AIGateway.complete()` → persistence), rate-limited routes, and a complete chat UI already wired to a topbar "Ask Vault" button — plus, from the immediately preceding phase's AI File Intelligence work, a generic `OpenAICompatibleCompletionProvider` behind `AIGateway.complete()`, already provider-agnostic by construction (ADR of that phase), selected via `Settings.completion_provider`/`completion_api_base_url`/`completion_api_key`/`completion_model_name`, defaulting to a deterministic stub (`ExtractiveCompletionProvider`) whenever no key is configured. Three questions needed resolving: whether to build a second conversation/assistant system or extend the existing one; whether to add the spec's literal `AI_PROVIDER`/`AI_MODEL`/`OPENROUTER_API_KEY` settings or reuse `COMPLETION_*` (OpenRouter is itself an OpenAI-chat-completions-compatible proxy, so no new provider code is needed either way); and how "tool calling" should actually work given the existing `CompletionProvider` Protocol's `complete(messages, context, max_tokens) -> text` shape has no function-calling concept.

**Decision:**
- **Extended the existing `ConversationService`/`Conversation`/`ConversationMessage`/chat UI rather than building parallel `assistant_conversations` tables or a second chat page.** `ConversationService.ask()` now branches: a question the intent classifier recognizes as a storage question dispatches to one or more tools instead of running `SearchService.search()`/`ContextBuilderService.build()`; everything else keeps the original retrieval path unchanged. Both paths persist through the same `ConversationMessageRepository`/`CitationRepository`, render in the same `chat.tsx`/`chat.$conversationId.tsx` pages, and share the same ownership/rate-limiting/routes — "Ask Vault" is one assistant with two internal answering strategies, not two assistants.
- **Reused `Settings.completion_*` for GLM-via-OpenRouter instead of adding `AI_PROVIDER`/`AI_MODEL`/`OPENROUTER_API_KEY`.** `COMPLETION_PROVIDER=openai_compatible` + `COMPLETION_API_BASE_URL=https://openrouter.ai/api/v1` + `COMPLETION_MODEL_NAME=<a GLM slug>` + `COMPLETION_API_KEY=<an OpenRouter key>` is the entire integration — zero new provider code, since `OpenAICompatibleCompletionProvider` already speaks OpenRouter's exact request/response shape. A second, parallel "which LLM" settings block controlling the same underlying `AIGateway` would be exactly the "duplicate business logic" the originating spec itself forbade. **Known tradeoff, not hidden:** `completion_*` is a *global* toggle — pointing it at GLM also switches the AI File Intelligence pipeline's strict-JSON extraction and this assistant's semantic-search answers to the same model. A chat-tuned model can be a worse JSON emitter than an extraction-tuned one. The escape hatch, if this ever bites in practice, is an additive `model_name: str | None = None` per-call override on `AIGateway.complete()` (default `None`, no existing caller changes) — documented here, not built, since nothing has demonstrated the need yet.
- **Tool routing is deterministic (keyword/regex intent classification), not real LLM function-calling.** `classify_intent(question) -> list[ToolCall]` (`apps/backend/app/application/assistant/intent.py`) maps a question to zero or more named tools via an ordered, most-specific-first rule table, with a storage-vocabulary fallback (unmatched storage phrasing still routes to `get_storage_overview` rather than falling through to semantic search over file content — the worst available failure mode, since it would answer an arithmetic question with irrelevant document snippets) and fixed, deterministic multi-tool bundles for compound questions (e.g. "how much am I wasting and what should I clean up" — two hardcoded patterns, not model-driven selection). This was chosen over extending the `CompletionProvider` Protocol into real function-calling (a `tools`-param, `tool_calls`-response shape) because that Protocol is shared by every existing `AIGateway.complete()` caller (this assistant, RAG chat, and the worker's file-intelligence extraction) — a disproportionate interface change for one feature, and the originating spec's own Section 9/10 explicitly prefers "simple rules... LLM only when explanation/reasoning is required" over an LLM-driven dispatch loop. Cost, stated plainly: paraphrase brittleness — a rule table cannot recognize every phrasing. Mitigated by the vocabulary fallback, a `vault_assistant_tool_used_total{tool="none"}` metric to observe real-world coverage over time, and a test asserting every example question from the spec, and every chat-page suggestion chip, routes correctly.
- **Ten tools (`apps/backend/app/application/assistant/tools.py`) wrap existing read-only services — `StorageIntelligenceService`, `DuplicateGroupRepository`, `SearchService`, `FileRepository` — none reimplement storage logic.** Every byte quantity ships as a `{x}_bytes: int` / `{x}_human: str` pair (`vault_shared.formatting.human_bytes`, already existed) so the model never computes byte→GB conversion itself — arithmetic is exactly where an LLM fabricates. `get_storage_overview` returns an explicit `available: bool`, `false` when no `StorageAnalysisSnapshot` exists yet (`StorageAnalysisSnapshot` itself carries no freshness/status field — freshness comes from the paired `StorageAnalysisJob`) — the single most load-bearing anti-fabrication field in the design, since without it "no analysis has run" is indistinguishable from "zero files" to the model. Every numeric tool argument passes through one shared `_clamp_int` (missing/non-numeric/negative → a named default; over-ceiling → the ceiling, echoed back in the result so a clamped threshold doesn't silently answer a different question than asked) with every ceiling traced to a `Settings.ai_max_*` field, asserted by a dedicated test. Organization/user identity is a `ToolContext` dataclass field, never an `args` dict key a model could theoretically supply — enforced structurally (every handler's signature is `(ctx, args)`, nothing else to read an id from) and asserted by a test that an injected `args["organization_id"]` changes nothing.
- **Fixed the one real bug the new persona system prompt surfaced:** `OpenAICompatibleCompletionProvider.complete()` inserted retrieved `context` at `messages` index 0 unconditionally. Adding a persona/injection-defense system prompt (`apps/backend/app/application/assistant/prompts.py`, `STORAGE_ASSISTANT_SYSTEM_PROMPT`, versioned) as `messages[0]` would then have landed *after* that context — an injection defense placed after the untrusted data it's meant to constrain isn't a defense. Fixed to insert context after any existing leading system-role messages instead of unconditionally at 0; backward compatible by construction, since no caller before this one ever passed a leading system message. The persona prompt is now prepended on *both* the tool path and the pre-existing semantic-search path — retrieved file *content* is, if anything, the more dangerous injection vector of the two, and it previously had no system message at all.
- **Tool-call rate limiting lives at the service layer (`ConversationService`), keyed by `{organization_id}:{user_id}`, not IP.** The route-level `conversation-ask` limiter (30/60s, pre-existing) is the hard stop for the endpoint; a second, narrower limiter is needed specifically for the more expensive tool-dispatch path, and route-level dependencies can't know in advance whether a given question will hit a tool. This required extracting the Redis INCR/EXPIRE primitive out of `rate_limiter()` (`presentation/dependencies/rate_limit.py`) into `check_rate_limit()` (`infrastructure/cache/rate_limit_counter.py`), landed as its own isolated, behavior-preserving commit — `application/` cannot import from `presentation/`, and `rate_limiter()`'s `Request`-shaped dependency signature isn't callable from a service method. On exceed: degrades to the existing semantic-search path rather than raising — this narrower limiter's job is shedding expensive work, not failing the request the route-level limiter already governs.
- **`ConversationMessage.tool_name` is a new nullable column, not a repurposed `retrieval_method`.** Not a style preference: `retrieval_method` is `String(20)`, and tool names like `get_storage_statistics`/`get_cleanup_candidates` don't fit. Migration `0015`, additive, no backfill, no index (never filtered on).
- **Tool-result caching follows the existing `get_cached_json`/`set_cached_json` (fail-open) pattern**, `ai_assistant:{tool_name}:{organization_id}:{args_fingerprint}` (SHA-256 of the sorted raw args, always including `organization_id` — asserted by a dedicated test), applied only to `get_storage_overview`/`get_storage_statistics`/`get_duplicate_summary`/`get_cleanup_candidates` (append-only data that only changes when a `StorageAnalysisJob` completes). **Known simplification:** the fingerprint hashes raw, pre-clamp args, not post-clamp — `limit=999` and `limit=10` (which clamp to the same effective value) get separate cache entries rather than sharing one. This costs a marginally lower cache-hit rate; it never returns a wrong cached value for a given input, since args→result stays consistent per raw-args signature. Not worth the complexity of duplicating each tool's clamp logic at the cache-key call site for a hit-rate optimization alone.
- **History passed to the completion provider is now bounded** (`ConversationMessageRepository.list_recent_for_conversation`, `limit=Settings.ai_max_history_messages`, default 6) on both the tool and semantic-search paths — a new method, not an optional `limit` param on the existing `list_for_conversation`, so the thread page's `get_detail` (which needs the *full* transcript) can never be accidentally truncated by a caller passing the wrong default. This incidentally fixes a pre-existing latent issue: `ask()` previously loaded and forwarded *every* prior message in a conversation to the completion provider, unbounded.

**Consequences:** With no completion provider configured (the default, matching the prior phase's stub-until-configured posture), tool-answered questions are formatted directly from the tool result (`render_deterministic_answer`) rather than routed through `ExtractiveCompletionProvider`'s generic context echo — factual storage questions answer *correctly* with zero LLM configured and zero network dependency, which is also what makes the whole feature fully testable in CI. OpenRouter's 402 (exhausted credits) is not distinguished from a transient failure — it falls into `OpenAICompatibleCompletionProvider`'s generic non-200 branch, mapped to `DependencyUnavailableError`, which the worker's file-intelligence Celery task would retry as if transient. A real, minor gap, not fixed this pass. "Why are these files duplicates?" as a bare follow-up (needing a remembered group id from a prior turn's prose) does not work — `get_duplicate_summary`'s result now carries enough detail (sample file names, checksum prefix, recommended-keep name) to answer "why" from the summary alone in one call, which is the fix that was made; true cross-turn entity memory (a `tool_result_ref` column, referenced by a future "these"/"that group" resolver) is deliberately not built, since nothing has demonstrated it's needed beyond this one example. `SearchService.search()`'s existing side effect (writes a `SearchSession` row and commits mid-call) is inherited unchanged by the `search_files` tool and by the semantic-search path — `ask()` was not, and is not now, one atomic transaction.

**Alternatives considered:** A second conversation/assistant system with its own tables and chat page (rejected — the spec's own instruction to reuse an existing conversation model if one exists applies directly, and fragmenting "Ask Vault" into two assistants would confuse the one entry point users already have); `AI_PROVIDER`/`AI_MODEL`/`OPENROUTER_API_KEY` as literal new settings (rejected — see Decision; a second LLM-selection toggle controlling the same `AIGateway` the first one already controls); real LLM function-calling via a `tools`/`tool_calls` extension to `CompletionProvider` (rejected — disproportionate blast radius across every existing caller of `AIGateway.complete()` for a feature the spec itself said to keep simple; the tool registry's `description` field is still populated on every `ToolSpec` so this upgrade path stays open without a rewrite if a future phase decides it's warranted); hard-raising `RateLimitExceededError` from the service-layer tool rate limit the same way the route-level limiter does (rejected — degrading to the existing RAG path preserves a useful answer instead of a hard failure, and the route-level limiter is already the actual protection against abuse); reusing `retrieval_method` for the tool name instead of a new column (rejected — physically doesn't fit, `String(20)`); persisting post-clamp args for the cache-key fingerprint (rejected as unnecessary complexity for a marginal hit-rate gain — see Consequences).

## ADR-025: Common Storage Abstraction (Phase 1 post-hardening) — a provider-independent `StorageAdapter` contract, explicit capabilities, normalized errors, and an adapter registry wrapping the existing Google Drive client

**Status:** Accepted

**Context:** Every service that touched storage — the Scanner, the Execution Engine, content extraction, the file-download endpoint — imported `GoogleDriveClient` and `GoogleWorkspaceOAuthClient` directly, constructed them in Celery task/DI composition roots, and worked with Drive-shaped types (`DriveFile`, page tokens, `drive_id=None` meaning "My Drive") throughout. This matched §8.1/§18's aspiration ("a connector is a leaf module... the rest of the pipeline does not change when a connector is added") in spirit but not in code: nothing actually stood between business logic and the Google-specific client. Phase 1 was scoped narrowly — build the common interface all future providers (Microsoft, Dropbox, local storage — §18) will implement, make Google Drive the one concrete adapter behind it, and migrate the existing consumers — without implementing any other provider, without changing behavior, without touching the database schema or invalidating a single connected account. A prior architecture-assessment pass (outside this phase) had already sketched a `vault_shared/storage/*` module later parked as `feature/storage-abstraction-and-content-analysis`; that branch was read for ideas but not merged — its models were untested and predated Phase 0's Execution Engine hardening (organization scoping, crash-retry idempotency, per-plan advisory locking), which this phase had to preserve exactly, not rebuild around.

**Decision:**
- **`vault_shared/storage/` is the contract package; `vault_shared/storage/adapters/` holds concrete providers; `default_registry.py` is the one composition-root factory.** `StorageAdapter` (`adapter.py`) is a `Protocol`, matching the codebase's existing preference for structural typing over ABCs — an adapter satisfies the contract by shape, no inheritance required, and a test can hand any object with the right methods to a service. `MUTATING_METHODS` is a frozenset of the nine mutating method names (`rename`, `move`, `copy`, `create_folder`, `trash`, `restore`, `permanent_delete`, `update_metadata`, `upload`), read by both the docstring's own claim and a static architecture test (`test_architecture_boundaries.py`) that greps every source file for a call to one of these names on a receiver that looks like a storage adapter — the same enforcement style Phase 0 already used for "only `ExecutionService` calls Drive write methods," now generalized past one provider's method names.
- **Provider ids, not internal ids, not filesystem paths.** `ProviderFileId` is a `NewType(str)` — not a bare `str` — so a database `File.id` (a UUID) and a provider's own id are different types at the type-checker level, not just by convention; every adapter method that addresses an item takes a `ProviderFileId`. This directly answers §13's file-identity concern and, concretely, prevents the exact bug class Phase 1's own review of the pre-abstraction code found latent (nothing enforced that `execution_step.planned_change["new_parent_id"]` was a provider id and not, say, a stringified UUID — it happened to always be correct by convention, never by type). `StorageFile.path` exists for display only; nothing in the adapter contract or the Execution Engine derives behavior from it, since Dropbox and local storage (§18) are path-based while Drive and a future Microsoft Graph adapter are id/parent-based — the contract is deliberately id-first so a path-based provider's adapter is the only place that ever computes a path from parent chains, exactly as Drive's own two-pass hierarchy resolution (ADR-016) already does downstream of the scanner today.
- **`StorageCapabilities` is one frozen dataclass with every flag defaulting to `False`**, plus a `Capability` `StrEnum` whose values are exactly the dataclass's field names (asserted by a test) — new capability, new field, nothing to keep in sync by hand. `capabilities.require(cap, provider=...)` is what an adapter calls before doing something it does not support, raising `StorageUnsupportedError` rather than the adapter silently no-op'ing or the caller having to `if provider == "google_drive"` first (§19's "Provider Agnostic" principle, now actually enforced by a static test rather than only stated). Google Drive's declared capabilities are all `True` except `supports_upload` — Drive's API can accept uploads, but no existing consumer needs it yet and building it unused would be exactly the "solve it before it's needed" §9 already warns against elsewhere; the capability honestly says `False` rather than claiming support for an unimplemented path.
- **One normalized error hierarchy (`storage/errors.py`) that *also* subclasses the pre-existing application error it replaces.** `StorageNotFoundError(StorageError, NotFoundError)`, etc. — every `except NotFoundError`/`except ForbiddenError` written before this phase, anywhere in the codebase (the Execution Engine's stale-state check, `ContentExtractionService`'s per-file forbidden handling, the file-download route), keeps working unchanged, and the HTTP status/JSON `code` an API caller sees is unchanged. `StorageUnauthorizedError`/`StorageAuthenticationRequiredError` are the one deliberate exception: both carry `http_status = 502`, not 401, continuing Phase 0's `AIUnavailableError` reasoning (§13.1) — a rejected *provider* credential is never the *user's* session expiring, and a stray 401 would make the frontend log the user out over a Drive-side problem. Only safe metadata is retained on an error (`provider`, a fixed provider error *code* — never a message body — `retry_after_seconds`, `request_id`); the Drive adapter's HTTP layer maps Google's specific quirks (403 meaning either a permanent per-item denial or a rate limit, distinguished only by `error.errors[0].reason`; `Retry-After` parsing) into this shape once, at the boundary, so nothing above it needs to know Google's error model exists.
- **`StorageAdapterRegistry` maps `connector.provider → factory → adapter`, memoized per connection for the registry's lifetime.** Built fresh per request (backend) or per task invocation (worker) via `build_storage_registry(db, oauth_client=...)` — deliberately not a module-level singleton (§19, and directly testable: a route test overrides the `get_storage_registry` FastAPI dependency with a registry backed by a fake adapter). Memoization is what keeps a scan or an execution job touching thousands of files at one adapter construction (one `ConnectorCredentialSource`, whose own 30-second token cache — see below — is what actually bounds request volume), not one per file. `StorageAdapterProvider` is the narrower Protocol (`adapter_for(connector) -> StorageAdapter`) every service actually depends on, so a test injects `StaticAdapterProvider(fake_adapter)` without touching the registry at all.
- **`GoogleDriveAdapter` wraps the existing `GoogleDriveClient` rather than rewriting it.** The client keeps its exact HTTP behavior (`list_files_page`, `list_changes_page`, `get_file`, the five mutating methods) and gained only what streaming/copy/create-folder/permissions/thumbnail/account-probe additions the contract needed that Drive's API already supports but nothing previously called; every new method follows the file's existing `_request`/`_get`/`_get_bytes` plumbing rather than introducing a second HTTP pattern. `ConnectorCredentialSource` (`storage/connector_credentials.py`) is the adapter's only door to credentials — it composes `ConnectorTokenService` (unchanged, still the one place a refresh token is decrypted) and adds a 30-second in-memory token cache, since the adapter's per-method calls would otherwise decrypt/possibly-refresh a token once per Drive API call instead of once per half-minute. No adapter method accepts or returns a credential (asserted by a contract test that inspects every public method's signature for parameter names containing "token"/"credential"/"secret") — `AIGateway`'s "no tools, no storage access" boundary (§12, Phase 0's AI boundary work) and this one compose without overlap, since neither the AI Gateway nor any adapter is reachable from the other's callers, and business services hold a `StorageAdapterProvider`, never a raw client or a token.
- **A `Revision` (`storage/models.py`) is a normalized stale-state token** — `token` (Drive's `headRevisionId` today; an ETag or content hash for a future provider) plus `modified_at`, with `differs_from` deliberately conservative: two revisions are declared different only when *both* carry a token and the tokens disagree, never from a timestamp alone (a rename or a permission change moves `modified_at` without changing content) and never when either side lacks a token (an item type, or a provider, that offers no content revision). `ExecutionPlanService._pre_state` now records the file's revision at plan-creation time; the Execution Engine's forward-step path (`_reject_if_stale`) refuses the step with `StorageStaleRevisionError` if the provider's current revision disagrees with what was reviewed — closing a real gap Phase 0 did not have a mechanism for (a plan approved against one version of a file, then blindly applied to a different one edited in between). This is additive to, not a replacement for, Phase 0's state-based retry detection (`_observe_progress`'s not-applied/applied/conflict three-way check) — the two guard different things: the revision check catches "the *content* changed since review," the retry-state check catches "the *mutation itself* already landed or was overtaken by someone else since the last attempt."
- **The Execution Engine, Scanner, content extraction, and the file-download service were migrated to the adapter; the Drive client itself was not deleted.** Each now takes a `StorageAdapterProvider` (Execution Engine, Scanner, Enrichment) or a registry (`FileService`) instead of `drive_client=GoogleDriveClient(...)` — every Celery task composition root (`worker/tasks/scan.py`, `enrichment.py`, `execution.py`) and the backend's `get_file_service` DI wiring were updated to build a registry via `build_storage_registry` and pass it down, per ADR-021's "promote to `packages/shared` once a second app needs it" precedent (the registry itself already lives there for exactly this reason). `_fetch_file_bytes`/`ContentExtractionService.extract` now call `adapter.export_format_for(mime, purpose)` with a purpose-specific export table (`ExportPurpose.ARCHIVE`/`DOWNLOAD`/`TEXT_EXTRACTION`) replacing three separate, slightly-different hardcoded MIME dictionaries that previously lived in `execution_service.py`, `file_service.py`, and `extraction.py` — same three real export choices as before (PDF/xlsx for archive and download, plain-text/CSV for extraction), now declared once, in the adapter, keyed by why the read is happening rather than duplicated per caller. `GoogleDriveClient` remains the only module importing `requests`/calling Google's HTTP API — nothing about this phase changes *which* module owns that; it changes who is allowed to construct and call it (only `GoogleDriveAdapter` and the registry, enforced by new architecture tests), same as Phase 0 narrowed "who may call the client's five write methods" to `ExecutionService` alone.
- **Reads are streams, bounded explicitly when a caller needs bytes.** `GoogleDriveClient.stream_file`/`stream_export` issue the request with `stream=True` and return a closeable chunk iterator (a small class, not a bare generator, so `close()` releases the connection even if a caller never starts iterating — a generator that is never advanced never runs its `finally`). `read_bounded(stream, max_bytes=...)` (`storage/reading.py`) is the one place a stream becomes `bytes`, raising `StorageContentTooLargeError` and closing the stream the moment the limit is exceeded — content extraction and the archive batch now pass an explicit `max_bytes` (their existing size caps, previously enforced only by checking `File.size_bytes` *before* downloading, which does nothing to stop a provider from sending more than it reported). The user-facing file-download route is the one path that stays a true stream end to end — `FileService.get_download_stream` returns the adapter's iterator directly to FastAPI's `StreamingResponse`, so a large download is never buffered whole in backend memory, closing a real, previously-latent gap.
- **A reusable contract test suite (`tests/storage_contract.py`), run against two independent adapter implementations.** `StorageAdapterContract` is ~50 behavioral tests (connection/health, paged scan, change detection, streaming reads bounded and unbounded, every mutation including idempotent trash/restore and not-found cases, and every normalized error kind with its retryability and credential-safety asserted) written once against the `StorageAdapter` Protocol's behavior, not Google Drive's — a future Microsoft/Dropbox/local adapter passes the identical suite by providing a "harness" (`tests/storage_testing.py`: seed a file, edit/rename/trash/delete it "externally," revoke credentials, inject a named failure) rather than writing a parallel test file. It already runs against `GoogleDriveAdapter` (via `FakeDriveApi`, an in-memory stand-in for Drive's HTTP surface — ADR-020's "fakes/mocks only" rule extended to this layer) and against a second, from-scratch `InMemoryStorageAdapter` that shares no code with the Google adapter, plus a third harness instance with every optional capability turned off — proving the suite is actually exercising the contract's capability-gating, not just Google's specific behavior.

**Consequences:** No database migration, no changed API response shape, no connector reconnection required — this is purely an internal-architecture change, as scoped. Every Phase 0 execution-security guarantee (organization scoping at the mutation point, crash-retry idempotency via rollback-record reuse, per-plan Postgres advisory locking, non-runnable-job rejection) is unchanged in behavior and re-verified by the full Phase 0 test suite passing unmodified against the migrated engine. `GoogleDriveClient` still exists and is still the only Drive HTTP caller — this phase adds a layer in front of it, it does not remove it, per §29's "same behavior + new abstraction, not new behavior + massive rewrite" instruction; deleting it is out of scope until a second provider adapter exists to prove the contract generalizes in practice, not just in the two-implementation test suite. The three previously-separate, near-duplicate native-export MIME tables are now one adapter method with a `purpose` argument — a minor, deliberate behavior-preserving consolidation, not a new feature. `upload()` exists on the contract and on `GoogleDriveAdapter` (raising `StorageUnsupportedError`) but nothing calls it yet; the capability is `False` and stays `False` until a real caller and its content-source-of-truth question (what does AI Vault upload, and from where?) are actually scoped, avoiding building an unused path per §9. `Revision`-based stale-state rejection is new, additive behavior a plan created before this phase (with no recorded revision) is exempt from by construction (`Revision.from_dict` on absent/malformed data returns `None`, and `_reject_if_stale` only fires when both sides have a token) — no in-flight plan is broken by this phase shipping.

**Alternatives considered:** Rewriting `GoogleDriveClient` itself to return the normalized shapes directly, collapsing client and adapter into one class (rejected — the client is a tested, working leaf module with no Drive-specific business logic of its own; wrapping it keeps "translate Drive's HTTP quirks" and "expose the provider-neutral contract" as two separable concerns, and a future provider adapter following the same wrap-don't-rewrite pattern only needs its own thin HTTP client, not a rewrite of this module's shape). An abstract base class instead of a `Protocol` (rejected — the rest of this codebase already favors structural typing for exactly this kind of pluggable-adapter role, e.g. `CompletionProvider`/`EmbeddingProvider` in the AI Gateway, ADR-018; consistency with an established pattern over introducing a second one). Deriving capabilities dynamically (a `try`/`except StorageUnsupportedError` probe, or inspecting the provider's own API metadata) instead of a static declared dataclass (rejected — a capability must be knowable without a network call, since the Execution Engine and UI both need to answer "can this be done" before attempting it, and Google's own API offers no such introspection endpoint to probe in the first place). Reviving and merging the parked `feature/storage-abstraction-and-content-analysis` branch wholesale (rejected — it predates Phase 0's execution hardening entirely, its models were never tested, and re-deriving the contract fresh against the now-hardened Execution Engine was safer than reconciling two independently-evolved designs under one merge). A single shared MIME/export table as a module-level constant imported by all three call sites, instead of an adapter method (rejected — the three callers genuinely want different target formats for the same source MIME type depending on *why* they're reading, which a bare constant dict cannot express without the caller itself branching on purpose; `export_format_for(mime, purpose)` puts that branch in the one place — the adapter — that should own provider-format knowledge).

## ADR-026: Remove the Approval step from directly-triggered execution plans — `require_approval` on `ExecutionPlanService`, permanent delete gated by a frontend confirmation dialog instead

**Status:** Accepted

**Context:** Every `ExecutionPlan` — whether created from a `Recommendation`, a `DuplicateGroup`, an ad-hoc Files-browser action (rename/move/archive), or a permanent-delete request — always created an `ApprovalRequest` in the same transaction (Phase 8 spec), and the backend's `POST /v1/execution-plans` route immediately called `ApprovalService.auto_decide_as_creator` right after, approving the plan and starting its job in a second round trip. No human ever actually reviewed anything at this step — "instant execution mode" (an earlier phase) had already made every non-permanent-delete plan auto-approve itself the moment it was created, so the `ApprovalRequest` row, its `ApprovalDecision`, and the two-call dance existed purely as unused scaffolding: a status a plan sat in for milliseconds, a decision no one made, a concept ("approval") surfaced in toast copy ("no approval step required") and a plan-detail "Approval" card that only ever said "auto-approved" or "no approval request found." Permanent delete was the one exception by design — its plan never auto-approved and stayed `PENDING_APPROVAL` until a human decided it from the Approvals page, on top of its own frontend type-to-confirm dialog. The founder asked for this removed: no approval concept anywhere in the product for a directly-triggered action, with a confirmation dialog kept only for permanent delete. Separately, the Automation Engine (Phase 9, ADR-021) has its own, distinct use of `ApprovalRequest`/`ApprovalDecision` — a `WorkflowPolicy`'s `REQUIRE_APPROVAL` effect on an `EXECUTE_ACTION` node, and plain workflow `APPROVAL` nodes with no `execution_plan_id` at all — genuinely meaning "a human must review this automated workflow's own step," a different question from "did anyone review this one-off rename," and not something the founder asked to change.

**Decision:**
- **`ExecutionPlanService.create_plan`/`create_plan_from_duplicate_group`/`create_ad_hoc_plan`/`create_permanent_delete_plan` all gained a `require_approval: bool = True` parameter**, threaded through the shared `_finalize_plan` (renamed from `_create_plan_with_approval`, since approval is now optional). Default `True` preserves every existing caller's behavior unchanged — critically, `apps/worker/worker/workflow/execution_service.py`'s `EXECUTE_ACTION` node still calls `create_plan()` with the default, so a `WorkflowPolicy`'s `AUTO_EXECUTE`/`REQUIRE_APPROVAL`/`SKIP` effect keeps meaning exactly what it always has. `False` is the new path: no `ApprovalRequest` is created at all; the plan is marked `APPROVED` and its `ExecutionJob` is created and enqueued in the same call, after running the identical permission pre-check (`validate_execution_permissions` against the plan's resolved connector/credentials) `ApprovalService.decide()`/`_check_permissions` always ran before approving — a missing write scope still fails the request synchronously and loudly, exactly as before, rather than silently succeeding and failing later on the worker. `ExecutionPlanService` gained an optional `enqueue_execution_job` constructor parameter (mirroring `ApprovalService`'s existing enqueue-callback injection pattern) for this; `apps/backend/app/application/execution_plan_service.py` (previously a bare re-export) is now a thin subclass injecting the backend's real Celery producer, the same shape as the pre-existing `ApprovalService` backend subclass.
- **Both backend routes now call with `require_approval=False`, unconditionally, including `POST /v1/execution-plans/permanent-delete`.** The one remaining gate for that irreversible action is the frontend's own `PermanentDeleteDialog` (a type-`DELETE`-to-confirm dialog, unchanged) — there is no server-side approval step left to additionally wait on for any action. `apps/backend/app/presentation/api/v1/execution_plans.py`'s `create_execution_plan` dropped its `ApprovalService` dependency and the `try/except VaultError` swallowing an auto-approval failure entirely; a plan that cannot start now fails the HTTP request itself (the router's own docstring states this plainly), rather than existing in the database `PENDING_APPROVAL` for a review nobody would ever perform. Because the failing permission check runs *before* the request's `_db.commit()`, a rejected plan leaves nothing behind — the request-scoped session's `close()` (in `get_db`'s `finally`) rolls back the flushed-but-uncommitted plan and its steps, so there is no dangling failed-plan row to clean up either.
- **`ApprovalService.auto_decide_as_creator` was deleted outright**, not deprecated — with the backend route no longer calling it, it had zero remaining callers anywhere in the codebase (confirmed by search before deletion), and per this repo's own standing rule (Handbook §26: delete dead code, don't comment it out), keeping an unused, untested-by-anything-real method around serves no one. `ApprovalService.decide()`, `bulk_decide()`, and `auto_decide_via_policy()` are all unchanged and remain the Automation Engine's real, still-used approval path.
- **The frontend's "Approvals" nav entry was removed** (`nav-items.ts`, which also drives the command palette's "Go to…" group) — Workflows/Workflow Policies were never linked into the app's navigation to begin with, so in the reachable product surface the Approvals page could only ever have shown direct-plan approvals, which no longer exist. The route file itself (`routes/approvals.tsx`) was left in place and fully functional, unreached by nav, in case a future phase wires Workflow policy management into the UI and needs it again — deleting working, correct code that a genuinely separate feature still depends on was judged out of scope for what was asked. Every toast and inline copy string across `rename-dialog.tsx`, `move-dialog.tsx`, `file-list-page.tsx`, `ai-file-result-list.tsx`, `storage-intelligence.duplicates.$groupId.tsx`, `archives.$archiveId.tsx`, and `recommendations.$recommendationId.tsx` that said "no approval step required" or similar was removed rather than left describing a concept that no longer exists; the `Recommendation.requires_approval` field (a stored column that was always `True` by default and never read by any branching logic) was dropped from the recommendation-detail UI for the same reason — displaying it would now be actively misleading, not just redundant. `execution-plans.$executionPlanId.tsx`'s "Approval" card (which queried `/v1/approvals` and rendered "no approval request found" for every plan, by construction, now that none is ever created) was replaced with a plain "Rollback" card carrying only the still-real rollback controls; its permanent-delete warning banner was corrected from "this one was not auto-approved and needs a real, deliberate decision" to reflect that it now also runs immediately once confirmed.
- **`PermanentDeleteDialog`'s success handling was rewritten** from "Sent for approval" with a "Review & approve" link to `/execution-plans/{id}` (a page that would have shown a plan forever stuck `PENDING_APPROVAL`, since nothing decides it anymore) to a plain "Permanently deleting now" toast — present-continuous, matching every other action's fire-and-forget phrasing, since this call is exactly as asynchronous as a rename or a move and the frontend does not wait for the worker to finish before reporting success.

**Consequences:** Every direct action in the product now behaves identically end to end: create the plan, it runs immediately, full stop — no status a user must understand beyond "it worked" or "it failed," no page to separately visit to make something happen. Phase 0's execution guarantees are untouched: the Execution Engine, organization scoping, crash-retry idempotency, rollback, and the full audit trail (`ExecutionAudit`/`AuditLogRepository`) all still fire exactly as before, just without the now-pointless approval hop in between plan creation and job start. A directly-triggered plan's audit trail now records `execution_plan_created` followed immediately by `execution_approved` (message: "No approval step required — this action runs immediately"), in place of the old `execution_plan_created` → (separate request) → `execution_approved` pair — same event vocabulary, one fewer round trip. The Automation Engine (Phase 9) is completely unaffected: `WorkflowPolicy` effects, `ApprovalRequest`/`ApprovalDecision` rows for workflow-triggered plans, the `approvals` API, and `ApprovalService.decide()`/`auto_decide_via_policy()` all work exactly as they did before this ADR — this was verified by leaving every one of those code paths untouched and confirming the full backend/worker/frontend test suites still pass. The Approvals UI page is now dead code from the perspective of the reachable app (nothing currently populates it), acknowledged rather than hidden; the moment a future phase gives Workflow Policies a real UI, that page becomes live again with no changes needed. No database migration was required — `approval_expiry_hours`, the `ApprovalRequest`/`ApprovalDecision` tables, and their repositories are all unchanged, since the Automation Engine still needs every one of them.

**Alternatives considered:** Deleting `ApprovalRequest`/`ApprovalDecision` and the `approvals` API entirely (rejected — the Automation Engine's `REQUIRE_APPROVAL` policy effect and plain workflow `APPROVAL` nodes have a real, distinct, unrelated meaning and genuinely depend on this table existing; removing it would silently break a separate, already-shipped Phase 9 feature the founder did not ask to change). Also deleting the `ExecutionPlan`/`ExecutionJob` tables and calling the `StorageAdapter` synchronously from the request handler (considered as one of the two options presented to the founder; rejected in favor of keeping the engine — the founder chose to keep Phase 0's audit trail, rollback, crash-retry idempotency, and per-plan advisory locking running underneath, invisibly, rather than trade all of that away for a marginally simpler request path). Making `require_approval` default to `False` instead of `True` (rejected — the one other caller, the Workflow automation engine's `EXECUTE_ACTION` node, must keep its exact current behavior with zero code change on its end; an opt-in default that every existing caller would need to override explicitly to keep working is exactly backward from a safe, additive parameter). Silently swallowing a permission failure in the `require_approval=False` path the way the old router's `try/except VaultError` did (rejected — that swallowing existed only because the old flow's failure mode was "leave it `PENDING_APPROVAL` for later," which no longer exists; with no approval queue to fall back to, a swallowed failure would instead be an execution plan the user believes ran but silently didn't).

## ADR-027: Organization Intelligence (Phase 2) — persisted Project/Client/Campaign entities, deterministic lifecycle and organization recommendations, the first production `AIGateway.recommend()` caller, and folder creation outside the ExecutionStep machinery

**Status:** Accepted

**Context:** After Phase 0 (AI reasoning-only boundary, hardened Execution Engine) and Phase 1 (`StorageAdapter`, ADR-025), AI Vault could index, enrich, classify, embed, and summarize individual files, and execute single-file actions safely — but it could not say *what a file belongs to*. No Project/Client/Campaign concept existed anywhere; no lifecycle judgment existed beyond Storage Intelligence's age buckets; no recommendation could propose a folder structure; and `AIGateway.recommend()` — the validated, non-authoritative reasoning path built in Phase 0 — had zero production callers. The Execution Engine also had no way to create a folder: every `ExecutionStep` targets an *existing* `files.id` (NOT NULL FK), and its crash-safety model compares a live provider item against captured pre/post state, which a not-yet-created folder does not have.

**Decision:**
- **One polymorphic `OrganizationEntity` table (`entity_type` ∈ project/client/campaign) plus `FileEntityLink`**, mirroring `Recommendation.category`/`KnowledgeAttribute.attribute_type`. `KnowledgeAttribute` was not reused: it has no organization scope, no central identity to dedup against, and a bare-string `source` rather than structured evidence. Dedup key is `(organization_id, entity_type, normalized_name)`. "Unknown is always allowed" is realized by the *absence* of a link — never a placeholder entity — and links below `ENTITY_LINK_MIN_CONFIDENCE = 0.5` are dropped, not stored weakly.
- **Entity inference is deterministic-first, AI-second.** `entity_clustering.build_clusters` forms connected components over signal-bearing files (classified or successfully extracted) using existing `FileRelationship` edges, shared folders, and matching normalized base names; a lone file never becomes a cluster. Clusters are capped at 15 files per AI call (oversized components are split by folder, never skipped) and 200 clusters per run. Only then does `EntityInferenceService` call `AIGateway.recommend()` with an `AIContext` whose per-file text is capped at 400 chars (summary first, extraction excerpt second) — reusing `RecommendationKind.CLASSIFY` and `ALLOWED_LABEL_KEYS` with **zero validator changes**. File content stays inside `<untrusted_data>`; the model sees only positional refs (`f0`, `f1`…), never database ids. `FileEntityLink.inference_version` makes re-runs skip already-linked files.
- **AI outage degrades, never breaks.** Mirroring `IntelligenceService`: an `INVALID_RESPONSE` for one cluster skips that cluster; other `AIUnavailableError`s are whole-run conditions (retried via the Celery task if retryable, failed otherwise). With only the stub provider configured, entity inference contributes nothing and the job still completes — lifecycle scoring and recommendation generation make no AI call at all.
- **Lifecycle is a pure deterministic scorer (`FileLifecycle`, PK=`file_id`)** reading duplicate membership, `SEQUENTIAL_VERSION` edges, entity links, and the same named age thresholds Storage Intelligence already uses. Age alone never yields a `*_CANDIDATE` state ("never equate old = delete"); conflicting/missing signals yield `REVIEW_REQUIRED`; no signal yields `UNKNOWN`.
- **Organization recommendations are a new table, generated deterministically.** `Recommendation`'s `(organization_id, rule_name)` identity cannot hold N per-entity proposals. One `GROUP_PROJECT|CLIENT|CAMPAIGN` row is proposed per active entity whose files span more than one folder, with `current_locations`, evidence, and a static destination (`Projects|Clients|Campaigns / <entity name>`) — no second GLM call to "choose" a folder name for an already-named entity. `estimated_storage_impact_bytes` is reorganized bytes, explicitly not savings. The other five `kind` values are reserved for future per-file proposals and are not generated yet.
- **Folder creation is a narrow public method on `ExecutionService` (`create_folder`), outside `ExecutionPlan`/`ExecutionStep`/`RollbackRecord`.** It keeps the one mutating call inside `execution_service.py` (so the exact-equality static guard still holds), re-checks connector/write permissions, enforces tenant isolation (another organization's storage source → not found, no provider call), persists the `Folder` via the same `FolderRepository.upsert` the scanner uses, and audit-logs. Crash-safety is deliberately stated as *narrower* than a step's: a crash between the provider call and the commit can orphan an empty folder, which the next scan rediscovers. The **moves** then go through the existing, unchanged `create_ad_hoc_plan(MOVE_FILE, require_approval=False)` path, so every Phase 0 guarantee (per-step verification, rollback, idempotent retry, advisory lock) applies to the part that actually relocates user files. `OrganizationRecommendationApplyService` receives an injected `ExecutionService`; the registry is built in `worker/tasks/execution.py`, an existing composition root.
- **Organizational memory is written from exactly one place:** `create_ad_hoc_plan`'s `MOVE_FILE` branch records a `CORRECTION` (confidence 1.0, an observed fact) when a user moves a file somewhere other than an active recommendation suggested. Corrections are fed back through the existing `AIContext.constraints` field; naming conventions through `naming_conventions`. No AI import enters `vault_shared/execution/`.
- **`NEAR_DUPLICATE` relationships come from a separate pass off `EmbeddingJob` completion**, because `RelationshipDiscoveryService` runs during enrichment, before embeddings exist. Mean-centering is computed over the whole batch for every comparison (a shrinking pool degenerates), pools are batched at 500, and exact-checksum pairs are excluded.
- **"Analyze Organization" is user-triggered only** (`POST /v1/organization/analyze`, owner/admin) — never auto-chained — because entity inference has real per-run model cost.

**Consequences:** One migration (0020, round-trip tested). `RelationshipType.NEAR_DUPLICATE` needed no migration. Entity endpoints live under `/v1/organization/entities` rather than `/v1/intelligence/entities` because the pre-existing `GET /intelligence/{intelligence_job_id}` would otherwise capture them (found by browser testing, covered by a router regression test). Real Google Drive behavior of `create_folder` is inherited from Phase 1's `GoogleDriveAdapter` and verified only against fake Drive clients in this environment — no live-Drive verification has been performed.

**Alternatives considered:** Nullable `target_file_id` plus an intra-plan dependency mechanism so a `MOVE_FILE` step could consume a `CREATE_FOLDER` step's runtime output (rejected — the FK points at `files`, not `folders`; `_observe_progress`/`_pre_mutation_state` have no meaning for an item with no provider id yet; and a "step N's output feeds step N+1" mechanism is strictly larger than the existing `CREATE_ARCHIVE` batch special case, all to protect a mutation that is trivially rediscoverable by the next scan). Three entity tables (rejected — identical shape, contrary to the codebase's discriminator convention). A second GLM call to name destination folders (rejected — cost and a second hallucination surface for no benefit). Folding near-duplicate detection into `RelationshipDiscoveryService` (impossible — embeddings do not exist yet when it runs).

## ADR-028: Ask Vault as a storage assistant — deterministic request understanding, structured answer blocks, provider-neutral conversation state, and confirm-to-execute through the Execution Engine

**Status:** Accepted

**Context:** Ask Vault answered storage questions through ADR-024's regex tool routing: a fixed set of read-only tools capped at 5–10 results, prose answers, citations as the only structured data, the full message history re-sent to the model each turn, and a system prompt telling the model it was read-only. It could not say "219 duplicate groups" and show all 219, did not understand "my local storage" or "them", and could not act — even though the Execution Engine (ADR-025/026) and the Local Agent can now perform real, verified changes.

**Decision:**
- **Understand deterministically first** (`vault_ai/understanding.py`): fixed patterns map everyday phrasing to a `Request` (kind, storage scope, file type, subject, folder name, which duplicate to keep, references to the previous result). Only a request that reads like an instruction but matches no rule is classified by the configured model (`ModelReasoning.classify`), into the same `Request` shape and validated identically. Questions about file content stay on the grounded retrieval path (ADR-022/024's citations, page-level since Phase 2, "I couldn't find that information in the connected files." when nothing matches).
- **Retrieve, don't dump** (`vault_ai/assistant.py`): every count, list and total comes from an index query (`FileRepository.query_files`, `SearchService.find`, Storage Intelligence listings, per-storage snapshots); no model call is made for them. Storage facts (`storage_context_service.py`) give each storage's indexed size, provider-reported usage, last sync and the operations its adapter really supports; results from a stale index carry a notice.
- **Answers are text plus structured blocks** (`conversation_messages.blocks`, migration 0028): `file_list`, `duplicate_groups`, `storage_summary`, `action_proposal`, `action_result`, `notice`. Lists carry their full id set server-side and only the first page client-side; `GET /v1/conversations/{id}/messages/{mid}/blocks/{n}` pages through the rest, so "show every duplicate" never silently stops at five. Ids are never shown to the user.
- **Conversation state belongs to AI Vault, not the model** (`conversations.state`): the last result set, the last folder created, pending proposals and a history of confirmed changes. "Move them into Finance" resolves against this state, so switching providers or models mid-conversation keeps the context; every id read back from state is re-checked against the organization before use.
- **Changes are proposals until confirmed.** The assistant only ever writes a pending proposal (with risk level, affected files and, for "organize", a folder-tree preview and the files left unsure). `POST /v1/conversations/{id}/actions/{action_id}/confirm` (owner/admin) runs `VaultActionService` — outside the AI layer, so the architecture guard keeps AI code free of execution imports — which creates folders through `StorageOperationService` (provider-confirmed before anything moves) and every file change as an ad-hoc plan in the Execution Engine. The answer lists each step with the action id the client follows to the provider-verified outcome. A proposal can run once; deleting is always "move to Trash", permanent deletion stays with Empty Trash.
- **The model reasons only where reasoning is needed** — organizing by project/purpose and suggesting names — over short references (F1, F2…), never real ids; unknown references, unsafe names and changed extensions are dropped and anything left out is reported as unsure. Without a model, organizing falls back to grouping by file type and says so.
- **The prompt (v4)** no longer claims the assistant is read-only; it says AI Vault can make changes the user confirms, never to claim a change happened, to show conflicting values from different files side by side, and to mention stale data.

**Consequences:** The ADR-024 tool path (`assistant/intent.py`, `registry.py`, `tools.py`, `rendering.py`) was removed with its tests; `assistant/prompts.py` remains. One migration (0028). Messages are now stamped at creation and ordered question-before-answer on ties, fixing transcripts whose question and answer shared a transaction timestamp. Streaming responses, per-task model routing and automatic provider fallback are not implemented; the gateway's retry/backoff (ADR-018) still applies.

**Alternatives considered:** Letting the model call tools directly (rejected — it would let model output choose queries and ids; the deterministic router gives the same coverage without a model call for most requests). Sending the full conversation to the model as memory (rejected — provider-specific, expensive, and lost on a model switch). Executing low-risk requests without confirmation (deferred — one consistent confirm step was preferred for the first version).
